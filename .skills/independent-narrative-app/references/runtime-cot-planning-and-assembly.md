## 作用

这本分册帮助作者和实现者把“生成前需要怎样检查、规划和组织输出”整理成可装配的 Prompt/COT 契约。社区把 COT 叫作思维链，但在独立应用中它也可以是规划清单、结构化中间结果、模型 reasoning 配置或只供系统消费的候选变化。

不能假设所有模型都会返回可见的隐藏推理。应用应依赖可验证的规划摘要、输出契约和候选变化，而不是依赖不可控的隐藏文本。

## 读取条件

- 需要决定是否使用 COT/规划模块，以及它解决什么问题。
- 需要把基础提示词和可选高级提示词拆成可维护模块。
- 需要迁移 ST Preset、`prompt_order`、role、Marker、宏、变量和输出标签的组装意图。
- 需要适配不同模型的 reasoning、结构化输出、Prefill、停止条件或无 reasoning 能力。
- 需要排查 Prompt 重复注入、顺序冲突、COT 泄漏、正文污染、预算超限或高级模块失效。

## 前置输入

- `Prompt Policy Package`：AI 职责、玩家主权、冲突政策、表达方向和输出意图。
- `Lore Runtime Contract` 与当前本回合正式状态、历史和认知边界。
- `Executable Profile Contract`：模型能力、Output Contract、Prefill 和降级链。
- `Prompt Assembly Contract`：消息 role、Marker、顺序、来源版本和 Trace。
- `Context Budget & Cache Plan`（若已建立）：上下文预算、缓存块和成本边界。
- Card-to-App 的 ST 预设、宏、正则和来源元数据（迁移任务才需要）。

## 先分清 COT 的几种含义

### 1. 规划清单

让模型在生成正文前检查当前目标、已知事实、在场角色、玩家输入、冲突和输出要求。它可以不显示给玩家，也可以只返回简短的结构化摘要。

### 2. 结构化中间结果

让模型先产生场景计划、候选动作、关系变化或待提交变化，再由 Parser、Kernel 或人工确认。中间结果是候选，不是正式事实。

### 3. 模型 reasoning 适配

如果目标模型有专用 reasoning 参数、独立通道或不可见思考，Profile 只记录能力、费用和输出边界。没有该能力时应有普通文本规划或直接生成的降级路线。

### 4. 玩家可见的思考文本

只有作者明确要求且内容模式允许时才启用。应将显示、下一轮可见性、保存和隐私分开决定；“不显示”不等于“从存档和模型输入都删除”。

## 普通 COT 与高级 COT

### 普通 COT 的固定组成

普通 COT 是保证一次 RP 回复不丢基本规则的最小规划层，通常由七部分组成：

1. **职责确认**：本次 AI 扮演什么职责，哪些内容由玩家控制。
2. **输入读取**：玩家刚说了什么，是否包含明确动作、问题、拒绝或补充设定。
3. **事实检查**：当前地点、时间、在场角色、已提交事件、关系和认知边界。
4. **角色检查**：本回合谁需要回应，各自知道什么、想要什么、会怎样说话和行动。
5. **推进计划**：本回合要回应、推进、保留或暂不解决的内容，避免循环复述和强行升级。
6. **输出计划**：正文视角、长度、结构、语言以及是否附带摘要、选项或候选变化。
7. **最终自检**：玩家主权、角色一致性、世界事实、格式、重复和禁写项是否通过。

普通 COT 可以是一段内部清单，也可以拆成多个 Prompt 模块。它不要求输出详细隐藏推理，只要求生成前真正覆盖这些检查点。

### 高级 COT 的可选组成

高级 COT 在普通 COT 基础上按需增加模块，不是简单写得更长：

- 多角色/群像调度：在场名单、发言顺序、镜头分配、沉默角色和关系张力。
- 多视角/场景编排：视角切换、镜头距离、节奏段落、场景进入与退出。
- Lore 与记忆检索：本回合需要的世界书、长期记忆、秘密和来源 revision。
- 关系与情绪规划：当前关系阶段、情绪变化条件、不得越级的边界。
- 剧情结构：目标、冲突、伏笔、回收、支线和长短期推进节奏。
- 玩法/状态规划：规则检查、资源约束、候选变量变化、任务和系统联动。
- 内容模式：SFW/NSFW 或其他模式对应的 Prompt、Lore、输出和模型隔离。
- 工具/多模型任务：检索、摘要、变量归约、图像或第二 API 的任务分工。
- 模型专项适配：reasoning 参数、Prefill、停止标记、结构化输出和降级。
- 质量修复：重复检测、格式修复、冲突消解、超长裁剪和失败回退。

高级模块必须有启用条件、输入、输出、Token 成本和失败回退；没有条件的高级模块会逐渐变成无法维护的常驻大 Prompt。

### 两者的区别

| 维度 | 普通 COT | 高级 COT |
|---|---|---|
| 目标 | 保证单次回复完整、连贯、不越权 | 处理多系统、多角色、多模型和复杂状态 |
| 模块 | 少量固定检查点 | 固定核心 + 条件模块 + 模型专项模块 |
| 输入 | 当前命令、核心事实、角色和输出要求 | 额外读取 Lore、Memory、玩法状态、工具结果和 Profile 能力 |
| 输出 | 正文计划和基础自检 | 结构化规划、任务分派、候选变化、修复或降级信息 |
| 宏 | 少量身份/基础变量占位 | 条件、状态、内容引用、模型能力和动态模块宏 |
| Token | 可预估且较稳定 | 随命中模块变化，必须单独预算和缓存 |
| 适用 | 大多数普通 RP 回合 | 群像、长期剧情、复杂玩法或高级预设 |

## 方法

### 1. 先确认为什么需要 COT

不要因为成熟预设里有 COT 就照搬。先写问题：是角色容易忘记目标、群像容易漏人、状态候选需要结构化，还是模型需要更稳定的输出格式。若普通 Prompt、Lore 和 Output Contract 已足够，就不新增 COT。

### 2. 分为基础提示词组和高级提示词组

基础组应保证作品基本运行，通常包括：

- AI 职责和玩家主权。
- 世界、角色和认知边界。
- 连续性和当前任务检查。
- 基础文风、视角或输出语言意图。
- 正文与候选变化的分离。
- 最小输出协议和最终自检。

高级组按作品需要启用，例如多视角规划、群像调度、关系阶段、复杂玩法候选、多模型任务、内容模式适配、特殊节奏或模型专项格式。高级组不能悄悄覆盖基础组的玩家主权、内容隔离和正式状态规则。

### 3. 为每个模块登记 owner 和用途

每个模块至少有：稳定 `moduleId`、名称、owner、目的、输入、输出、作用域、条件、优先级、插入意图、可否裁剪、所需 Profile 能力、版本、来源和失败回退。

模块正文只写该模块的规则，不把角色设定、世界书全文、数据库字段或另一个模块的重复说明塞进来。一个模块如果无法说清“什么时候需要、谁消费、失败后怎么办”，就还没有设计完成。

### 4. 设计组装顺序和消息角色

可以从以下基线开始，再用冲突案例调整：

```text
安全与宿主边界
→ AI 职责和玩家主权
→ 世界/角色核心与内容模式
→ 当前正式状态和确定性规则
→ Lore 选择结果
→ COT/规划模块
→ 历史与记忆
→ 玩家当前命令
→ 输出协议与最终检查
```

`system`、`developer`、`user`、`assistant` 等 role 受目标 API 能力约束；role 不是作品内的权威等级。用 Marker 标明来源、版本和用途，避免把模型角色名误认为事实来源。

### 5. 规定固定、条件和高级模块

- 固定模块：每次生成都必须存在的最小纪律。
- 条件模块：只有模式、阶段、任务、关键词或能力满足时启用。
- 高级模块：用户或作者主动打开，或由已记录的 Profile 选择。

条件判断只读取允许的已提交状态和本回合输入。不要用模型自己刚写出的候选变化决定同一回合是否注入更高权限规则。

### 6. 为高级 COT 建立宏清单

宏是装配工具，不是 COT 本体。高级 COT 常见宏按用途分为：

| 宏类型 | 用途 | 例子与边界 |
|---|---|---|
| 身份宏 | 注入玩家、角色、作品和会话身份 | ST 常见 `{{user}}`、`{{char}}`；独立应用映射到自己的受控字段 |
| 内容宏 | 引用 Prompt 模块、角色片段、世界书块或输出协议 | 只引用已登记 ID，不允许任意文件路径 |
| 状态宏 | 读取已提交变量、地点、时间、关系或任务 | 只读 base revision，不在组装阶段写状态 |
| 历史/记忆宏 | 引用最近消息、摘要、检索结果或热事务 | 必须遵守认知作用域和 Token 预算 |
| 条件宏 | 按模式、阶段、角色在场、任务类型或能力选择模块 | 条件不成立时有明确空值或替代模块 |
| 模型宏 | 选择 reasoning、Prefill、格式、语言和 Profile 专项内容 | 能力来自验证，不用模型名称猜测 |
| 随机/时间宏 | 生成可复现的选择、日期或世界内时间 | 随机结果或种子进入 Trace，不能偷偷改变正式状态 |

项目自定义宏要使用独立命名空间并记录版本。示例写法可以是 `{{rp.state.location}}`、`{{rp.module:scene-plan}}` 或条件块，但它们只是独立应用的设计示例，不宣称为 ST 标准语法。

### 7. 规定高级宏的使用链

高级宏按以下顺序执行：

```text
扫描宏与来源
→ 识别 ST 兼容宏 / 项目宏 / EJS 或未知表达式
→ 检查作用域、权限、模式和 base revision
→ 选择需要的 COT 模块与 Lore/Memory 输入
→ 在受控解释器中求值和转义
→ 重新计算实际 Token 与缓存边界
→ 组装 role/Marker/prompt_order
→ 记录展开摘要、失败和降级
```

宏值为空、字段缺失、递归、超长或目标模型不支持时，使用预先声明的空值、替代模块、关闭高级模块或阻止发送。未知宏默认保留并报告，不静默删除；EJS、正则和脚本属于可执行边界，不能当普通宏直接运行。

迁移 ST 预设时保留 `prompt_order`、模块开关、COT 起止标记、显示正则和宏的来源关系，再决定原生重实现、构建期转换、降级或不支持。

### 8. 借鉴 ST 预设而不复制预设

可迁移的结构包括：模块变量、条件开关、`prompt_order` 意图、模型专用分支、COT 起止标记、输出格式和显示正则之间的关系。

不能直接复制具体作者文本、模型人格、破限条目、NSFW 文案或插件调用。成熟预设是结构样本，不是本 Skill 的跨作品 Prompt 正文。

### 9. 保持正文、规划和候选隔离

至少区分：

- `StreamDraft`：流式草稿，可取消，不是 COT 事实。
- `RawModelResponse`：完整原始响应，未校验，不直接展示为正式内容。
- `PlanningSummary`：经过协议识别的规划摘要，仍是候选输入。
- `CandidateChangeSet`：待 Kernel 裁定的变化。
- `CommittedFacts`：经过权限、Schema、冲突检查和 Save 确认后的正式事实。

正文中写“已经发生”不代表变量已经提交；COT 里写“应该发生”更不代表世界状态已改变。

### 10. 设计降级链

- 模型不支持 reasoning：使用普通文本规划、结构化摘要或直接生成。
- 高级 COT 模块冲突：关闭高级模块，保留基础组。
- 规划格式失败：正文可以按项目策略保留，但候选变化为空或进入人工确认。
- Token 不足：按 Assembly Contract 的优先级裁剪，不偷偷删除玩家主权、输出协议或关键状态。
- COT 泄漏到正文：通过 Parser/Renderer 隔离或安全回退，不把隐藏文本当正文。

每种降级都要记录原因、影响、是否重试和最终使用的 Profile。

### 11. 验证组装效果

至少准备：普通 COT 完整性、高级模块未命中/命中、宏缺值、宏递归、未知宏、模块重复、顺序冲突、无 reasoning 模型、输出截断、正文污染、候选变化和模式隔离案例。验证关注不变量、Prompt Trace、Output Contract 和行为结果，不要求不同模型逐字输出同一段 COT。

## 面向小白的提问顺序

1. Skill 先自动带上普通 COT 的七项基础检查，不要求小白从空白设计。
2. 根据群像、长期剧情、玩法状态、多模型和内容模式判断是否推荐高级 COT。
3. 向作者解释新增高级模块解决什么问题、增加多少复杂度，再请求确认。
4. 宏扫描、作用域、求值顺序和降级由 AI/实现者整理；作者只确认哪些动态能力允许存在。
5. 最后总结普通/高级模块目录、宏清单、顺序、作用域和未决风险。

用户说“不知道”时，Skill 可以提供最小基础组草案，但要标记为建议，不代替作者确认内容模式和输出协议。

## 唯一产物

`COT Assembly Plan`：普通 COT 七项组成、高级 COT 模块目录、输入输出、owner、启用条件、宏清单与作用域、role/Marker、组装顺序、宏求值阶段、正文/候选隔离、降级矩阵和验证案例。

## 轻量路径与升级

- 小型项目：使用普通 COT 七项检查，可合并成少量模块，但不能漏掉玩家主权、事实、角色、推进、输出和自检。
- 多角色、多玩法或长对话：增加结构化规划、条件模块、状态候选和 Prompt Trace。
- 多模型、ST 迁移、复杂宏、内容模式、可见/隐藏 reasoning 或频繁超预算时：增加宏注册表、Profile 能力矩阵、版本化模块、Golden Assembly 和降级回归。

## 交接与验证

- Prompt Policy 决定“应该遵守什么”；本册决定“规划模块怎样装配”。
- Lore Runtime 提供选择结果；Prompt Assembly 决定最终消息链；Profile/Output Contract 决定模型能力和解码方式。
- Token 分册负责估算、缓存和成本观测；Kernel 负责候选裁定和正式提交；UI 分册决定是否显示安全的规划摘要。

## 不负责

不创作世界书和角色正文，不决定作品的具体文风，不执行 ST/EJS/正则代码，不直接请求模型，不提交状态，不把隐藏推理当作必然可见内容，也不决定页面结构。
