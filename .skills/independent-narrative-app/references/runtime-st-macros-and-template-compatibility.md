# ST 宏与模板兼容

## 作用

保留 ST 角色卡、世界书和预设中的宏知识，并让作者选择独立运行时的兼容档位。该选择是运行时能力决定，不强制所有项目实现宏。

## 读取条件

来源内容含 `{{...}}`、作者希望导入 ST 资产、项目使用自定义模板，或需要排查宏未展开、作用域错误和版本差异时读取。

## 前置输入

- 来源角色卡、世界书、预设及其目标 ST/扩展版本证据。
- `Host Foundation Contract`、`Prompt Assembly Contract` 或 Lore 作用域。
- 作者选择的兼容目标和安全边界。

## 方法

### 1. 先扫描依赖

在转换前列出：宏、EJS 模板、MVU 变量调用、正则脚本、前端脚本、扩展专用字段和未知表达式。文件能导入不代表这些依赖能执行。

### 2. 选择兼容档位

| 档位 | 目标 |
|---|---|
| 完整兼容 | 针对明确 ST/扩展版本实现并回放所需宏集合 |
| 核心高频兼容 | 实现项目实际使用且经测试的常用宏，其余保留并报告 |
| 不启用运行时 | 不求值 ST 宏，但数据库保留语法、来源和影响说明 |

可以额外提供自定义宏，但必须独立命名、定义作用域和版本，不能伪装成跨版本 ST 标准。

### 3. 建立宏能力清单

按来源版本核对，不把下列示例写成所有版本的完整保证：

- 名称与角色字段：`{{user}}`、`{{char}}` 等。
- 局部/全局变量：`{{getvar::name}}`、`{{getglobalvar::name}}` 等读取形式。
- 随机与选择：`{{random::...}}`、`{{pick::...}}`、`{{roll::...}}` 等。
- 历史、时间、运行状态、消息位置和实用宏。
- 模板、嵌套、条件或控制流能力。

每个宏记录：规范名称、样例、参数、输入作用域、输出类型、纯函数/副作用、求值时机、嵌套规则、未知值行为、目标版本和测试夹具。

### 4. 规定作用域与求值顺序

区分作品、存档、角色、会话、消息、世界书条目和本次 Assembly 作用域。推荐顺序：来源选择/权限过滤 → 绑定 base revision 的上下文 → 解析模板 → 由内到外或按目标版本规定求值 → 转义 → 实际 token 预算 → 装配。

顺序必须以目标版本/引擎测试为准。随机宏要记录种子或结果；变量宏只能读取允许的已提交状态，不能在 Prompt 组装中静默写状态。

### 5. 处理未知与错误

未知宏、参数错误、递归循环和版本不匹配默认保留原文并写入兼容报告。项目可以选择警告、替代文本或阻止发送，但不得静默删除。设置最大嵌套深度、展开长度和运行时间。

### 6. 区分相邻技术

- EJS 是可执行模板能力，不等于普通宏；默认不运行不可信模板。
- MVU 是变量/状态插件体系，不是独立应用必备运行时；迁移时提取语义和规则。
- 正则可用于显示后处理或协议解析，但不得成为关键状态的无约束猜测器。
- 脚本/插件是代码执行边界，必须隔离、授权和审计。

### 7. 建立夹具

为每个支持宏保存输入文本、作用域快照、目标版本、期望输出和错误行为。组合测试覆盖嵌套、未知宏、转义、随机、缺变量、秘密作用域和预算变化。

## 唯一产物

`Macro Compatibility Contract`：兼容档位、宏能力清单、作用域/求值顺序、版本差异、未知宏策略、安全限制、兼容报告字段和测试夹具要求。

## 轻量路径与升级

- 新项目不使用宏：选择“不启用运行时”，但保留导入扫描与兼容报告能力。
- 导入含未知/嵌套/版本宏，或宏进入 Lore、Prompt 和状态作用域时升级到版本化解释器与完整夹具。

## 交接与验证

- ST Bridge 负责来源盘点；Lore/Assembly 在规定阶段调用兼容层；Integration 保存展开 Trace。
- 对每个声明支持的宏做精确夹具回放，并测试未知、循环、恶意长度、缺变量和版本不匹配。

## 不负责

不强制项目实现 ST 宏，不自动执行 EJS/MVU/脚本，不创作 Prompt 或世界书正文，也不把某一版本行为宣称为跨版本事实。
