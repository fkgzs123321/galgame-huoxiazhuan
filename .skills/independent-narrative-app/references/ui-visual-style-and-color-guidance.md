## 作用

这本分册帮助作者回答“这个 RP 世界在玩家眼前应该是什么样子”。它从风格锚定、配色与材质选择一路走到 UI 结构方向，让界面服务角色、剧情和游玩氛围，而不是做成换了颜色的通用后台。

它是 Skill 知识库中的按需 reference，不是某个具体项目的 UI 设计稿，也不是固定页面模板。作者可以采用、混合、修改或完全放弃书中的方向。

## 读取条件

在以下情况读取：

- 作者刚开始讨论作品的 UI 气质，还不能用清楚的词描述想要的感觉。
- 需要把题材、玩家体验和视觉语言联系起来。
- 需要制定配色、字体、边框、圆角、阴影、图标、插画、背景或动效方向。
- 现有界面“能用但不像这个作品”，需要找出视觉不一致的原因。
- 需要复查颜色对比、文字可读性、状态颜色和不同内容模式的隔离。

不要因为项目存在一个按钮或一张页面就自动读取本册。它服务的是视觉判断，不是功能实现。

## 前置输入

- `Project Profile` 或作品轮廓草案：题材、内容形态、主要体验和目标设备。
- `World Contract`、`Character Portfolio`、`Content Mode Contract`：作品的气质来源、角色关系和内容模式。
- 作者喜欢、讨厌或想参考的视觉印象；没有参考时允许从文字形容开始。
- 已有项目的截图、设计变量或组件清单（如果任务是改造，而不是从零开始）。

## 先分清本书不做什么

本册可以提供页面结构和系统呈现方式的参考，但不能替作者拍板。具体有哪些系统、哪些信息长期可见、玩家怎样进入它们，仍由作品设计决定；本册负责把这些决定转化为符合 RP 气质的界面构成。

正文的文风、视角、角色语言和叙事节奏属于 `rp-style-and-expression.md`。正文如何被前端排版和渲染属于 `ui-narrative-reading-and-message-rendering.md`。设置有哪些选项属于 `ui-settings-and-preferences.md`。

## 方法

### 1. 先从作品气质开始

不要先问“要不要做侧栏”或“按钮放在哪里”。先写三到五个能描述作品的词，例如克制、热烈、神秘、轻快、压迫、温柔、机械感或手工感。

每个词都要能回答三个问题：

1. 玩家在界面中应该感受到什么。
2. 哪些视觉元素能支持这种感受。
3. 哪些元素会破坏这种感受。

如果作者只能说“高级”“好看”这类宽泛词，Skill 应提供可比较的解释，例如“高对比、少装饰、窄色相范围”或“低对比、暖色纸张、细边框”，而不是直接替作者选方案。

### 2. 从世界、角色和叙事提取风格锚

RP 前端的视觉锚不只来自题材名称，还来自玩家与世界的关系：玩家是在阅读故事、与角色相处、使用世界内的装置、管理一支队伍，还是同时进行多种活动。

可以从以下来源提取锚点：

- 世界：时代、地域、技术、文化、材质和公共符号。
- 角色：代表角色的气质、关系距离、语料、习惯物品和情绪色。
- 叙事：轻松日常、压迫悬疑、冒险推进、群像切换或长期陪伴。
- 玩法：阅读、对话、探索、管理、战斗、经营或多系统联动。
- 世界内媒介：书信、日记、手机、终端、档案、地图、手册或其他符合设定的载体。

风格锚不等于把角色立绘贴在所有角落。它应转化成颜色、材质、字体、边界、信息出现方式和交互节奏。

### 3. 把风格拆成几个可讨论的轴

不必每次全部填写，选择真正影响作品的轴即可：

- 明亮 / 阴影：决定整体明暗和情绪重量。
- 克制 / 装饰：决定背景、纹理、边框和装饰的数量。
- 亲密 / 冷静：决定圆角、留白、字体和颜色的柔和程度。
- 手工 / 工业：决定纸张、噪点、线稿或网格、刻度等语言。
- 安静 / 强反馈：决定状态颜色、动效和操作反馈的醒目程度。
- 传统 / 未来：决定字形、符号、材质和信息标记的时代感。

这些轴是帮助作者表达偏好的工具，不是必须二选一的评分表。混合方向时要记录哪些元素来自哪一轴，避免最后变成互相冲突的装饰集合。

### 4. 建立配色关系，而不是只挑几个喜欢的颜色

至少区分以下颜色角色：

- 画布色：页面或阅读区域的基础背景。
- 表面色：面板、输入区、消息块等与画布相邻的层次。
- 主文字与次文字：正文、说明、弱化信息的文字层级。
- 品牌/主题色：表达作品身份或主要操作的颜色。
- 强调色：少量吸引注意力的颜色，不能取代所有状态色。
- 语义色：成功、提醒、危险、禁用、加载和冲突等状态。

颜色选择需要同时考虑对比度、面积和出现频率。大面积高饱和颜色会增加疲劳；低对比文字会损害长篇阅读；把危险、成功和剧情重点都染成同一个颜色会让玩家无法理解状态。

明暗模式、SFW/NSFW 模式、作者工具和玩家界面如果需要不同色彩，应记录它们的隔离规则。只改变一个开关而继续复用会泄露内容或让状态含义改变，不能算完成。

### 5. 处理字体和文字层级

字体方向应服务内容：长篇正文优先稳定阅读，标题和章节标识才承担个性表达。至少记录正文、标题、标签、辅助说明和错误信息的字号、字重、行高、字距和最大阅读宽度意图。

不要为了“有风格”给每种角色或每段正文换字体。字体数量越多，界面越难维持一致；特殊字体还可能在目标设备缺失。需要特殊字形时准备回退字体，并检查中文、拉丁字符、数字和符号是否完整。

### 6. 定义表面、边界和密度语言

记录圆角、边框、阴影、分隔线、纹理、透明度和留白的总体倾向：

- 细线、少阴影、较多留白通常更安静、清晰。
- 厚边界、明显阴影、紧凑密度通常更有工具感或控制感。
- 大量玻璃、模糊和半透明会增加层级，却可能损害对比度和性能。

这里描述的是视觉规则，例如“所有交互表面使用同一组边界和阴影层级”，不是规定页面必须由哪些面板组成。

### 7. 让界面保留 RP 韵味

RP 前端应让玩家先感到“我正在进入一个世界或与角色相处”，再意识到自己正在操作软件。可采用以下手法，但不要求全部使用：

- 让作品、场景或角色成为首屏信号，而不是只在导航角落显示名称。
- 让章节、时间、地点、关系或状态以符合世界观的方式出现。
- 让切换系统像翻页、打开终端、查看手册或进入场景，而不是每次都像打开管理后台。
- 让重要角色通过语气、头像/立绘、色彩、动作反馈或关系变化形成存在感。
- 让系统反馈与剧情互相解释，例如任务变化、消息到达或地点解锁有叙事语境。

避免把 RP 页面做成大量同形卡片、通用数据看板或没有作品身份的组件展示。工具感可以存在，但必须与作品的主要体验匹配。

### 8. 从风格锚落到具体 UI 结构

Skill 应根据作品内容给出二到三个结构方向，并说明取舍，不能只讨论颜色：

| 结构方向 | 核心构成 | 适合情况 | 常见风险 |
|---|---|---|---|
| 叙事阅读型 | 正文/对话是主轴，状态和玩法通过抽屉、浮层或次级入口出现 | 长篇、陪伴、恋爱、悬疑和重剧情作品 | 系统入口过深，状态反馈不及时 |
| 角色陪伴型 | 角色形象、对话、关系和即时反馈围绕主要互动区域组织 | 单角色/少角色陪伴、日常与关系推进 | 角色装饰挤压正文，长期内容难扩展 |
| 世界内媒介型 | 用手机、终端、日记、档案、地图或其他设定内载体承载功能 | 作品存在明确媒介，强调沉浸和探索 | 拟物过度、功能可发现性差 |
| RPG/系统型 | 正文与角色仍保留主位，数值、地图、任务、背包等形成稳定系统区 | 冒险、战斗、经营、策略和沙盒 | 容易变成后台面板，削弱角色与剧情 |
| 混合型 | 一个主要 RP 舞台，加若干独立玩法页面或世界内入口 | 多系统长期作品 | 导航和视觉语言容易分裂 |

结构草案至少说明：主要 RP 舞台、输入区、长期可见信息、次级系统入口、当前状态反馈、返回剧情的路径和移动端收拢方式。作者可以混合方向，但需要指定哪个是主轴，避免每个系统都争夺首屏。

### 9. 统一图标、装饰和动效

图标应先决定符号语言，再选择具体图标：线性、实心、像素、印章、机械刻度或手绘都可以，但同一层级不要混用过多风格。装饰元素必须有作用：营造气氛、区分层级、提示状态或强化作品身份；纯装饰不应遮挡正文或影响操作。

动效需要记录触发条件、持续时间、可取消性和减少动效时的替代表现。生成流、状态变化和错误反馈应有清晰而克制的反馈，不能用连续闪烁掩盖真实状态。

### 10. 给方向做比较，而不是给作者下结论

Skill 可以提供二到三个文字方向，每个方向写清：

- 视觉关键词和代表性的颜色关系。
- 适合的内容体验和设备环境。
- 主要优点、主要代价和常见误用。
- 哪些部分可以借用，哪些部分不建议混合。
- 对应的 UI 结构主轴、系统入口方式和移动端取舍。

比较的目的，是帮助作者更快发现自己的偏好和风险。作者可以说“都不喜欢”或只抽取其中一部分，Skill 应根据反馈更新方向卡，而不是把比较结果当作已确认设计。

### 11. 做基础可读性检查

至少检查：正文与背景的对比度、弱化文字是否仍可读、颜色是否不是唯一状态信号、键盘焦点是否明显、触摸目标是否足够、减少动效后信息是否仍完整、窄屏文字是否不会被裁切。

这一步是视觉方向的可行性检查，不等于完整的 UI 无障碍验收。实际组件实现后仍需由质量分册和真实设备测试确认。

### 12. 形成视觉与结构方向记录

将已确认内容写成短记录：作品气质词、世界/角色视觉锚、主色关系、文字层级、表面语言、主要 RP 舞台、次级系统入口、图标/装饰语言、动效原则、禁止项、可变项和待确认项。保留作者明确“不做”的选择，避免后续 AI 又把被否决的方向捡回来。

## 面向小白的提问顺序

未来用户说“我不知道 UI 怎么做”时，Skill 按一次一个关键决定的方式引导：

1. 先问作品希望给人的整体感觉，并给出几个通俗解释。
2. 找出能代表世界、角色和主要玩法的视觉锚。
3. 再问更偏明亮还是阴影、更偏克制还是装饰，并讨论颜色、字体和材质。
4. 根据作品内容给出二到三个 UI 结构方向及影响，由作者确认主轴。
5. 最后总结已确认、暂定、可修改和明确不做的内容。

如果用户暂时没有偏好，Skill 可以给出一份暂定方向记录，但必须标记为“建议草案”，不能写成项目事实。

## 唯一产物

`RP Visual & Composition Brief`：作品气质词、世界/角色视觉锚、视觉轴、配色角色、文字层级、表面语言、主要 RP 舞台、系统入口方向、图标/装饰与动效原则、可访问性提醒、禁止项、可变项和确认状态。

## 轻量路径与升级

- 小型项目：三到五个气质词、一个视觉锚、一套颜色角色、一个主要 RP 舞台和三条禁止项。
- 长期 RP、多模式、作者工具与玩家界面并存时：增加模式隔离、语义色表、字体回退、动效偏好和设备检查。
- 多玩法系统时：增加主轴/次级系统关系、世界内入口、返回剧情路径和移动端收拢方案。
- 有完整设计系统或多主题时：增加设计令牌、版本、迁移规则和组件视觉回归。

## 交接与验证

- 交给完整设计方案、设置分册和具体 UI 实现，作为视觉约束和取舍依据。
- 交给正文渲染分册，说明长文本、消息块和状态提示的视觉层级。
- 验证重点是可读性、语义色一致性、模式隔离、作者确认状态和实现前后的风格一致性。

## 不负责

不替作者决定作品包含哪些功能，不直接实现页面、组件树、技术栈或数据库，不创作 Prompt/COT/模型文风，也不提交正式状态。它可以提出 UI 结构方向，但最终结构必须回到作品内容与作者确认。
