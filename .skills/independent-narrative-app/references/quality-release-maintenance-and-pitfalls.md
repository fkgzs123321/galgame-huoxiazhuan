# 发布、维护与坑点导航

## 作用

在阶段或全局收口时汇总可运行性、兼容、迁移、安全、安装包、回滚和已知限制，并把常见症状路由到权威分册。它决定证据是否足够，不复制各领域修复方法。

## 读取条件

阶段验收、内部交付、公开发布、版本升级、长期维护和故障复盘时读取。

## 前置输入

- `Stage Control Record`、`Behavior Evidence Package`、`Integration Evidence Package`。
- 版本/迁移/安全/平台证据、发布资产、目标设备和支持范围。
- 未解决风险、已知限制和回滚入口。

## 方法

### 1. 确认发布对象和版本

分别标记应用、内容包、状态 Schema、世界书格式、Prompt/Profile、Output Contract、宏兼容和资源包版本。说明支持矩阵和最低版本，避免只用一个应用版本掩盖数据兼容。

### 2. 执行发布门

至少核对：

- 目标用户核心流程可从安装/启动完成，而非只在开发服务器运行。
- 行为、集成、保存重开、迁移和模式隔离达到确认标准。
- 目标平台的打包、路径、权限、离线/断网和资源缺失已测试。
- 密钥、日志、导出包和第三方来源通过 Trust 检查。
- 旧档/旧内容的支持、降级和拒绝信息明确。
- 回滚包、备份和恢复步骤实际可执行。

### 3. 区分交付等级

内部原型、作者试玩、公开测试和稳定发行使用不同门槛，但都要标明真实级别。没有真机、真实模型或发布包证据时，不用“已完成”代替“开发环境通过”。

### 4. 生成验收与已知限制

使用 `../assets/templates/acceptance-report.md`，列出通过、失败、未验证、证据链接、影响、临时措施和 owner。已知限制要写用户何时会遇到、结果是什么、怎样避免或恢复。

### 5. 发布、监控与回滚

发布包记录哈希、构建环境、依赖锁、内容清单和签名/来源。分批发布时定义观察信号和停止条件。回滚需处理应用版本、Schema、内容包和资源，不假设降级应用能读取升级后的存档。

### 6. 建立维护节奏

保存回归夹具、迁移样本和兼容样本；每次更新判断哪些 owner 产物和版本受影响。重大事故记录时间线、根因、影响、恢复和防复发证据，而不是只记录最终补丁。

### 7. Pitfall 路由

| 症状 | 先看证据 | 权威入口 |
|---|---|---|
| 世界书没出现/乱触发 | Lore Trace、Prompt Trace | Lore Runtime / Assembly |
| 角色知道不该知道的事 | 来源作用域、Memory/Lore Trace | World / Character / Memory |
| UI 状态与正文不同步 | commandId、revision、Save ACK | Turn-State / UI / Save |
| 取消后仍写入 | Gateway 终态、durable 时间 | Gateway / Turn-State |
| 读档后关系倒退 | CommitRecord、迁移、Memory 重建 | Save / Memory |
| 模式关闭仍泄漏 | Prompt/Lore/缓存/存档 | Content Mode / Trust |
| ST 卡导入后功能缺失 | 来源依赖和兼容分类 | ST Bridge / Macro/Profile |
| 只在开发环境可用 | 平台能力、打包日志 | Platform / Release |

表格只导航；具体判断回到 owner，避免这里形成第二套规则。

## 唯一产物

`Release-Maintenance Gate`：发布级别、版本/兼容矩阵、验收报告、发布包证据、已知限制、回滚/恢复、维护策略和 Pitfall 索引。

## 轻量路径与升级

- 本地个人交付：启动入口、核心流程、保存重开、包清单/哈希、已知限制和恢复入口。
- 公开发行、跨平台、远程更新、不可逆迁移或敏感数据时增加签名、分批、支持矩阵和事故演练。

## 交接与验证

- 发布建议交给 `SKILL.md` 更新 Gate State；失败回到对应 owner 和 Stage Control。
- 最后从干净环境安装/启动，按用户可见入口运行核心流程，验证包清单、哈希、旧档、回滚和删除范围。

## 不负责

不复制领域修复教程，不自行推进阶段，不隐藏未验证项，也不把“构建成功”当作完整发布验收。
