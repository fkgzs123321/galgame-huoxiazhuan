# 玩法系统与主剧情联动

## 作用

指导任何玩法或叙事辅助系统先建立自身框架，再与主剧情、角色认知、Memory 和其他系统形成受控联动，避免功能成为脱离作品的孤岛。

## 读取条件

作品包含玩法系统、工具界面、叙事辅助能力，或需要排查不同入口中的人物/事实断裂时读取。

## 前置输入

- `Discovery Draft Package`、`Narrative Contract`、`World Contract`、`Agency Contract`。
- 现有状态、界面、存档和跨系统问题证据。

## 方法

### 1. 先用白话确认系统身份

帮助用户回答：它是什么、玩家为什么使用、能做什么、不能做什么、怎样改善 RP 体验。主动提供 2–3 个范围方案和推荐，不要求小白先定义 Command、Event 或 Projection。

### 2. 独立设计系统

每个系统先说明：

- 玩家入口、核心行动、成功体验和边界。
- 内部功能、页面/状态、规则与权限。
- 正式数据、初值、谁能提议、谁能提交、生命周期。
- 空状态、加载、取消、失败、重试、离线、读档和恢复。
- 简单版本和什么证据出现后才升级。

不要先画 UI 就假设业务规则已经明确。

### 3. 建立与主剧情的双向联动

记录：

- 主剧情怎样触发或读取系统。
- 系统行为怎样形成候选事实、事件或叙事反馈。
- 角色何时知道系统中发生的内容；私有信息不得自动变成全员知识。
- 关系、任务、物品、地点等共享事实由哪个 owner 提交。
- 同一 NPC 在不同入口怎样读取同一身份、关系和已提交记忆。

如果系统内已经与某角色建立关系，而正文仍按陌生人处理，视为联动失败；反过来，私聊内容无授权泄露给正文角色也属于失败。

### 4. 建立多系统关系

不强制所有系统两两直连。优先通过 Command、提交事件、State Contract 和只读 Projection 解耦。每条联动写清：来源、触发、读取、裁定、写入、知情范围、叙事反馈、失败和重复保护。

### 5. 分层验证

先独立验证系统自身，再验证与主剧情的双向联动，最后验证多系统、生命周期、保存重开、取消和重复 commandId。

## 唯一产物

`Gameplay-Narrative Contract`：系统设计卡、功能边界、正式状态需求、主剧情双向联动、角色知情范围、多系统交接和验证场景。

使用 `../assets/templates/system-design-card.md`。

## 轻量路径与升级

- 简单系统：一页设计卡 + 一张联动表。
- 多系统、长生命周期、共享状态冲突、实时/并发或复杂恢复时升级 Command/Event/State Contract 和时序图。

## 交接与验证

- 交给 Turn/State、UI、Memory、Save 和 Integration Trace。
- 验证独立、双向、多系统、认知隔离、读档和失败恢复。

## 不负责

不预设手机、地图、相册等固定系统，不选择数据库、事件总线或 UI 框架，不允许 UI 直接写正式状态。
