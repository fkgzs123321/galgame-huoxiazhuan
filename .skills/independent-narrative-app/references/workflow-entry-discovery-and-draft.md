# 创作发现与初步草案

## 作用

把模糊想法整理成可修订的作品轮廓，不直接生成完整应用。只拥有 `Discovery Draft Package`；Task Envelope、路由和 Gate State 由 `SKILL.md` 管理。

## 读取条件

- 从零创建且没有可复用 Project Profile。
- 用户希望探索作品定位、内容轮廓或初步系统框架。
- Card-to-App 或已有应用审计发现目标产品边界未知，并阻塞后续工作。

已有权威产物足以完成局部角色、世界书、系统、诊断或实施任务时跳过本册。只缺少一个局部边界时产生 Profile Delta，不重新询问整部作品。

## 前置输入

- `Task Envelope`。
- 用户原始想法、现有卡、应用资料或其他来源证据。
- 已知的明确不做项和现实限制。

## 方法

### 1. 先问创作内容

不要先问商业定位。先帮助用户说清：

- 同人还是原创；同人基于什么作品、采用什么时间点或改编幅度。
- 主要人物与关系形态：单角色、群像、预设主角、可生成角色等。
- 内容类型和尺度：叙事、恋爱、后宫、冒险、经营、策略、SFW/NSFW 或混合。
- 预计游玩长度：短篇、长期、可重复、可持续生成或跨世界式无限。
- 希望玩家得到什么体验，以及不希望出现什么。

“无限”不仅指进入不同世界，也包括可持续生成角色、客户、事件、经营周期或新局面的开放构造。

### 2. 建立初步框架

整理而不是补完：

- 核心 RP 循环与玩家主要行动。
- 初步世界、玩家身份、主要角色、开局和剧情方向。
- 可能需要的玩法或叙事辅助系统。
- 独立应用大致形态、目标平台和内容包边界。
- 已知依赖、风险、未知和明确排除。

每项标记为 `已确定/暂定/灵感/待讨论/明确不做`。不得把“灵感”自动升级成实施需求。

### 3. 用决策支架提问

- 一次只推进一个关键决定。
- 给 2–3 个候选及影响，明确推荐适合当前证据的方案。
- 用户不知道时先给可修改草案，再询问是否接近，而不是反复要求用户定义术语。
- 不用某个现有项目或单一示例替作者决定题材、系统和字段。

### 4. 收口

全文总结，检查内容、系统和目标平台是否互相矛盾。只在用户确认后，把草案交给领域分册或可行性门。

## 唯一产物

`Discovery Draft Package`：

- Project Profile：来源、内容轮廓、RP 核心、目标玩家体验、长度和模式。
- 初步内容框架：世界、玩家、角色、开局、剧情和表达方向。
- 初步系统框架：每个候选系统的目的和联动意图。
- 成熟度登记：已确定、暂定、灵感、待讨论、明确不做。
- 未知项、风险和来源引用。

使用 `../assets/templates/project-profile-and-draft.md`。

## 轻量路径与升级

- 局部任务：只补所属作品、已有边界、预期产物和必要 Delta。
- 来源矛盾、产品边界冲突、内容与运行时混淆时，升级为完整发现。
- 不在本阶段解决技术栈、数据库接口和逐文件计划。

## 交接与验证

- 将实际涉及的内容交给对应 `rp-*.md`。
- 进入结构与完整设计时交给 `workflow-feasibility-and-design-gates.md`。
- 验证下游不需要重复提问、每项决定有来源和成熟度、明确不做项未被重新加入。

## 不负责

不建立 Task Envelope，不决定全局路由和 Gate State，不撰写完整领域契约，不开始编码。
