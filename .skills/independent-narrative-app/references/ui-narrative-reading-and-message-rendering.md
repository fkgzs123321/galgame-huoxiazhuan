## 作用

这本分册定义前端怎样安全、稳定、易读地显示正文、对白、旁白、系统消息、状态摘要和流式生成内容。它关注阅读层级、排版、富文本安全、长文本、流式过程、回看和不同设备的一致体验。

它不规定模型应该写什么，也不把 UI 临时显示当成正式事实。

## 读取条件

- 设计或改造正文阅读区、对话消息、旁白、系统提示和状态块。
- 需要支持 Markdown、有限富文本、代码/结构化块、图片或附件。
- 需要处理流式输出、取消、解析失败、消息编辑、重生成、回看、复制、搜索或导出。
- 排查正文被截断、布局跳动、标签泄漏、富文本注入、状态栏与正文混乱或回放不一致。

## 前置输入

- `Visual Direction Brief` 和作品的阅读优先级。
- `Executable Profile Contract` 的输出契约、消息类型和 Marker 规则。
- `UI Command-Projection Contract` 的状态与错误模型。
- 目标设备、文本长度、语言、辅助功能和内容模式要求。

## 先分清内容所有权

模型文风、视角、角色语料和动作表达属于 RP 内容分册；本册只决定这些内容如何被前端显示。正文中的变量、状态候选和系统标记不因被渲染出来就成为正式状态，必须经过 Output Contract、Kernel 和 Save 的提交链。

## 方法

### 1. 先定义消息类型

至少区分项目实际存在的类型：用户输入、正式正文、角色对白、旁白、系统消息、状态摘要、流式草稿、候选变化、错误和调试信息。每类记录来源、是否进入历史、是否可复制、是否允许富文本和是否能被下一轮 Prompt 使用。

不要用颜色或一个 HTML 类名代替类型契约；同一消息在无障碍模式、纯文本导出和窄屏下仍应保持语义可辨识。

### 2. 先确定需要渲染多少层

渲染层数由作品内容决定，不是越多越高级。先从以下层级中选择：

| 层级 | 职责 | 典型产物 |
|---|---|---|
| L0 原始层 | 保留模型或存档原文，不执行、不美化 | `RawModelResponse`、正式消息原文 |
| L1 协议层 | 识别 Marker、正文、状态块、选项、摘要和错误 | 受控消息块、解析结果 |
| L2 语义层 | 把内容归为旁白、对白、动作、内心、系统信息等 | 语义节点/AST |
| L3 美化层 | 应用排版、颜色、角色标识、背景、分隔和主题 | 可读正文视图 |
| L4 交互层 | 加入折叠、选项、媒体、复制、搜索、锚点和操作反馈 | 交互式阅读视图 |
| L5 独立系统层 | 用只读 Projection 展示状态、任务、关系或其他玩法 | 与正文同步但不写回原文的系统视图 |

常见选择：

- 基础两层：L0 + L3，适合纯文本和极简短篇。
- 标准四层：L0 + L1 + L2 + L3，适合大多数长期 RP。
- 完整六层：需要正文附加块、复杂交互和独立玩法 Projection 时使用。

无论选几层，L0 原文与正式状态来源都要保留。美化层和交互层可以重建，不能反向篡改已提交事实。

### 3. 建立阅读层级

正文优先保证行长、字号、行高、段间距和对话辨识度。标题、场景转场、角色名、时间地点、系统块和状态摘要需要有清楚但不过度的层级。长篇阅读应避免把每句话拆成卡片，也避免让装饰挤压文字。

文字层级要继承视觉方向，但不能让颜色成为唯一信号。可用标签、图标、边框、结构化标题或语义化 HTML 辅助区分。

### 4. 选择正文美化风格与形式

正文美化要与作品的 RP 舞台一致，常见形式包括：

- 小说式：连续段落、章节/场景标题、对白与旁白在同一阅读流中，适合重叙事和长文。
- 聊天式：角色头像、姓名、气泡或消息列，适合陪伴、日常、手机媒介和多人交流。
- 舞台/剧本式：角色名、台词、动作和场景说明分栏或分行，适合群像和强对白作品。
- 日记/书信式：日期、纸张/手稿语言、章节收藏和批注感，适合回忆、慢节奏与世界内媒介。
- 档案/终端式：记录编号、时间戳、状态标签和结构化段落，适合调查、科幻、管理和系统叙事。
- 混合式：主正文使用一种稳定形式，手机、回忆、战报或系统消息使用受控的次级形式。

Skill 应说明每种形式对长文、移动端、角色辨识、可访问性和性能的影响。不要每段随机换样式，也不要为了美化把一句话拆成大量嵌套卡片。

### 5. 规定富文本安全边界

解析流程应是：识别允许语法 → 解析为受控 AST/节点 → 清理标签、属性、URL 和资源 → 应用安全渲染器 → 记录被拒绝内容。默认禁止任意脚本、事件属性、危险 URL、未授权 iframe、跨源资源和可执行模板。

Markdown/HTML 的兼容程度由项目声明。未知扩展保留原文或显示为安全文本，不为了“看起来正常”执行它。

### 6. 稳定处理流式输出

流式过程应有独立的 `StreamDraft` 表现：可取消、可更新、可显示不完整提示，不能直接写入正式历史。解析器在增量文本不完整时不能反复拆坏结构；必要时使用纯文本回退或安全的增量边界。

完成信号、解析成功和正式提交是不同事件。保存失败、解析失败或取消后，草稿应消失、标记失败或转为候选，不得继续使用“已完成正文”的样式。

### 7. 处理正文附加块

如果项目允许正文携带状态栏、摘要、选项或变量块，必须定义稳定 Marker、允许字段、可见性、顺序、转义和失败回退。正文显示层只渲染已通过协议识别的块；未识别内容显示为普通文本或进入诊断，不直接执行。

另一种路线是正文纯文本，状态和变量完全由独立 Projection 显示。两种路线都可以，必须在 Output Contract 中明确，不能同一项目一半依赖正文解析、一半依赖 UI 猜测。

### 8. 保证历史、编辑和回放一致

保存正式正文时记录 revision、消息 ID、来源类型、渲染版本和必要的原始数据。编辑、重生成、分支和回放要说明哪些是新消息、哪些替代旧消息、哪些只改变显示。

渲染器版本变化时，旧消息需要可回放或有明确迁移；不能因当前 CSS 或解析器变化而让历史内容含义改变。

### 9. 设计复制、搜索和导出

复制应提供正文纯文本和必要的结构化选择；搜索应能定位消息、角色、章节或系统标记；导出应说明是否包含隐藏/调试内容、候选状态和元数据。复制与导出不得绕过内容模式、隐私和权限。

### 10. 处理错误、空状态和长内容

至少有加载、空会话、生成中、取消、解析失败、内容被过滤、保存失败、消息缺失和离线状态。长文本使用稳定的虚拟化或分段策略时，不能破坏复制、搜索、锚点和屏幕阅读顺序。

### 11. 控制渲染卡顿

性能优化由实现者负责，作者只需确认阅读体验和目标设备。至少采用与项目规模相称的策略：

- 流式阶段只增量更新当前消息，不在每个 token 到达时重解析全部历史。
- 对 chunk 合并和渲染刷新做节流，避免高频 DOM/组件更新。
- 缓存已经完成的语义解析和富文本 AST；内容或渲染版本不变时直接复用。
- 长历史使用窗口化/虚拟列表，但保留搜索、复制、锚点和屏幕阅读的正确顺序。
- 角色头像、插画、音频和复杂媒体按需加载，离屏内容暂停重动画。
- 避免大面积模糊、持续阴影动画、每层独立观察器和深层卡片嵌套。
- 流式结束后再执行昂贵的完整语法高亮、目录、关系标注或媒体增强。
- 提供低动效、低性能或纯文本降级，降级后正文与关键操作仍完整。

性能验收至少记录：首屏时间、首 token 到可见时间、长历史滚动、单条超长正文、连续生成、内存增长和窄屏输入响应。不能只凭开发机“感觉不卡”得出结论。

### 12. 面向小白的提问顺序

先问正文是阅读主轴还是系统面板的附属内容，再让作者选择小说、聊天、舞台、日记/书信、档案/终端或混合形式。随后由 Skill 根据正文附加块、交互和玩法系统建议渲染层数，并自动补充性能与安全底线，不要求小白自己设计渲染管线。

## 唯一产物

`Narrative Rendering Contract`：消息类型表、选定渲染层数、正文美化风格、阅读层级、渲染语法白名单、流式状态、正文附加块协议、历史/回放、复制搜索导出、性能预算、降级路线、错误状态和设备验收标准。

## 轻量路径与升级

- 小型项目：纯文本/有限 Markdown、单一正文流、基础流式草稿和保存回看。
- 长篇、多角色或移动端：使用标准四层，增加分段、章节锚点、增量解析、历史窗口化、搜索、复制、响应式和辅助功能矩阵。
- 正文附带状态、多格式资源、多模式或高风险内容：增加交互层和独立 Projection、AST 安全层、版本化渲染器、性能预算、回放夹具和隔离验收。

## 交接与验证

- 从 `Executable Profile` 接收 Output Contract，从 Kernel/Projection 接收已提交内容和状态。
- 视觉表现参考 `ui-visual-style-and-color-guidance.md`；模型表达继续由 `rp-style-and-expression.md` 负责。
- 验证层级边界、正文美化一致性、富文本攻击、未闭合标签、流中断、取消、解析失败、保存失败、回放、长历史卡顿、内存增长、窄屏、键盘、屏幕阅读、复制和导出。

## 不负责

不创作剧情和模型文风，不决定 Prompt/COT，不执行脚本或宏，不提交正式状态，不直接调用数据库或模型 API，也不决定页面导航和功能结构。
