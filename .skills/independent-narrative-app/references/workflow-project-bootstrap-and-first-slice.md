## 作用

把已经完成设计确认的独立 RP 应用落到真实项目中，并用一条范围受控的垂直切片证明内容、运行时、UI、模型和保存可以接通。它提供技术栈中立的实施顺序和项目配方要求，不把 Web、PWA、Tauri、Electron 或某个框架设为所有项目的固定答案。

## 读取条件

- 完整设计方案和阶段路线图已获得实施确认。
- 从零创建项目、接入已有仓库、Card-to-App 首次落地或需要补第一条可运行回合。
- 既有项目需要在保留当前行为的前提下补工程边界、测试入口或恢复证据。

## 前置输入

- `Project Profile`、`Complete Design`、`Host Capability Contract` 和当前 `Gate State`。
- 目标平台/宿主、已有仓库规则、运行命令、依赖和未提交改动。
- 第一切片的真实用户动作、成功结果、非目标、失败语义和验证环境。
- 内容包、模型接口或 Model Stub、存储接口及最少测试数据。

## 方法

### 1. 工作区预检

先读取真实仓库、嵌套 `AGENTS.md`、包管理器、启动命令、测试命令、环境变量模板、未提交改动和现有行为证据。已有项目优先沿用当前框架、构建工具和目录边界；不因为新 Skill 的推荐结构而顺手重写无关代码。

预检记录至少包含：

- 当前入口、运行/构建/测试命令和可用工具。
- 目标平台与实际能力缺口。
- 内容、Runtime、Platform、UI、Storage、Gateway 和测试的当前 owner。
- 已知用户改动、兼容约束、密钥/个人数据风险和可回滚基线。
- 本阶段允许、禁止和暂不处理的动作。

### 2. 裁定技术栈与宿主

先列能力，再选最小实现。使用 `runtime-host-foundation-and-content-pack.md` 和 `runtime-platform-and-assets.md` 判断是否需要本地文件、系统密钥、后台任务、多窗口、离线、安装包、跨设备或服务端密钥。

- 已有项目：默认沿用已有技术栈，只有证据表明它无法满足目标时才提出迁移。
- 新项目：根据目标平台、团队能力、离线/性能/发布要求和维护成本选择方案。
- 只做本地原型：可以使用 in-process 和内存/文件存储，但仍保留正式状态与保存边界。
- 需要桌面能力：再裁定 Tauri、Electron 或其他宿主，不把桌面壳提前写入内容契约。
- 没有真实需求时，不为“未来可能多平台”预建复杂跨平台抽象。

输出技术栈裁定时必须写明：选择、未选择的替代方案、依据、影响、可回退路径和仍未验证的环境风险。

### 3. 建立职责边界

目录名称可以随项目调整，但依赖方向和 owner 必须清楚。一个最小项目通常需要能识别以下职责：

```text
内容与兼容层
  → 内容包、角色、世界书、Prompt/Profile、资源和来源保留
运行时核心
  → Command、回合、候选变化、revision、原子提交和 Trace
模型网关
  → 请求、流式、取消、重试、错误和 Model Stub
存储与迁移
  → Save/Load、CAS、Schema、恢复和旧档策略
平台 Port
  → 文件、密钥、网络、时钟、后台任务和媒体能力
UI/Projection
  → 输入、草稿、已提交事实和调试视图
测试与发布
  → 契约、行为、集成、打包、安装和回滚证据
```

UI 不直接写数据库或调用模型适配器；内容文件不直接提交正式状态；派生 Memory、摘要和缓存不能成为第二事实源。小项目可以暂时放在一个仓库或少量模块中，但每个职责仍要有明确的接口和测试入口。

### 4. 建立最小工程基线

初始化或接线后先让项目可以重复执行：

1. 固定 Node/运行时和包管理器版本，生成锁文件和安全的环境变量模板。
2. 建立最小启动、构建、格式/类型检查和测试命令。
3. 添加一个不需要真实密钥的 Model Stub、最小内容包和可重复测试数据。
4. 创建 Git 本地基线；需要远程备份时按铁律 12 检查密钥、个人数据和版权资产后再请求上传 GitHub。
5. 确认开发服务器、生产构建和测试目录不会读取开发机绝对路径或真实玩家存档。

如果已有工程缺少这些命令，先补可验证基建，不把“项目能打开”描述成应用已完成。

### 5. 实现第一条垂直切片

第一条切片优先选择最小但能证明闭环的动作：加载一个作品/角色 → 建立新会话 → 接收一次玩家输入 → 装配最小 Prompt → 使用 Stub 或已确认 Gateway 获取响应 → 形成正文和候选变化 → 校验权限/格式/revision → 原子提交 → Projection 展示 → Save → 关闭并重开恢复。

切片必须明确：

- 哪些内容、状态、Prompt、UI、平台和存储是真正需要的。
- 哪些高级功能明确不在本阶段，例如多角色、复杂 Memory、第二平台或真实迁移。
- 按 `quality-integration-diagnostics-and-traces.md` 建立完整强制覆盖矩阵；逐项记录状态、证据、影响/延期、owner 和再验证入口，不用总括句隐藏缺项。
- 每个提交点的 commandId、revision、Trace 和可观察证据。

### 6. 接入真实模型或目标宿主

Stub 闭环通过后，单独增加真实模型、流式、目标平台或资源能力。不要在同一阶段同时引入多个高风险变量。真实模型验证必须区分：请求是否发出、Prompt/Lore 是否正确、响应是否可解析、候选是否被授权提交、Save 是否确认耐久和 UI 是否回放一致。

### 7. Definition of Done

第一切片只有在以下条件都被标记后才算完成：

- 新项目或已有项目能从记录的命令启动。
- 至少一条真实玩家动作产生可观察结果。
- 正式事实只能由统一提交入口改变。
- 解析/保存失败和冲突不污染或静默覆盖状态。
- 至少一次保存、退出、重开恢复通过。
- 有契约/行为/集成证据或明确标为未验证。
- 强制覆盖矩阵场景、合法状态和证据列完整；缺项时只能标记有条件通过或未验证，不能标记完整通过。
- Save ACK 使用与实际耐久证据匹配的名称，损坏/备份恢复策略已登记。
- 与下一阶段的接口、非目标、风险和回滚入口已记录。

## 唯一产物

`Implementation Bootstrap Record`：工作区预检、技术栈/宿主裁定、职责和依赖方向、工程基线、第一切片范围、命令/文件/接口、Definition of Done、验证证据、未解决风险和回滚入口。它与 `Host Foundation Contract`、`Stage Control Record` 配套，不替代二者。

## 轻量路径与升级

- 已有稳定项目只补缺少的启动/测试/保存入口，不重新搭建目录。
- 纯文字短篇可以先使用单包、单角色、单模型和本地存储；仍需保留四态和提交边界。
- 长期游玩、跨平台、复杂 Memory、旧档迁移、真实发布或多人协作时，升级为独立的工程阶段并增加备份、迁移预演、平台验证和回滚演练。

## 交接与验证

- 将内容职责交给 RP 分册和 Bridge，将提交/保存/模型/平台职责交给对应 Runtime 分册。
- 将第一切片交给 `quality-behavior-specs-and-regression.md` 与 `quality-integration-diagnostics-and-traces.md`。
- 将打包、安装、发布和长期维护交给 `quality-release-maintenance-and-pitfalls.md`。
- 验证必须从干净目录或记录的真实工作区命令开始，区分 Stub、真实模型、开发环境、目标平台和发布包证据。

## 不负责

不选择所有项目都必须使用的技术栈，不替作者决定作品内容，不携带完整 starter 仓库，不绕过设计确认直接写生产代码，也不把工程骨架通过一条命令伪装成完整应用。
