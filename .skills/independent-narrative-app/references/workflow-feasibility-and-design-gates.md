# 可行性与完整设计门

## 作用

在实施前证明关键设想能够成立，并把内容、运行时、系统联动和质量标准整理为完整设计。只提供 gate criteria、evidence 和通过/退回建议；`SKILL.md` 更新 Gate State。

## 读取条件

- 草案进入结构讨论、关键可行性检查或完整设计。
- 新功能影响多个系统或引入新的模型、平台、数据、兼容能力。
- 现有证据不足以判断实施成本、失败边界或验收方式。

## 前置输入

- `Task Envelope` 与当前 Artifact Index。
- `Discovery Draft Package`（执行过发现流程时）。
- 已选 RP/桥梁产物、代码库证据、目标环境和现实限制。

## 方法

### 1. 绘制系统关系

按项目实际系统建立结构图，不机械要求固定模块。每个系统标明：

- 自身目的、玩家行动和体验价值。
- 输入、正式状态、命令、输出与生命周期。
- 与主剧情、角色认知、Memory、Prompt、UI、Save 的读写方向。
- 唯一状态 owner、失败处理和验证入口。

### 2. 检查关键可行性

| 维度 | 必须确认 |
|---|---|
| 内容 | AI 能否在不破坏玩家主权、角色和世界边界下持续生成 |
| 模型 | 目标模型是否支持长度、结构化输出、流式、内容模式和成本要求 |
| 运行时 | 回合、状态、Prompt、Lore、Memory、Save、诊断是否形成最小闭环 |
| 数据 | 初值、写权限、revision、迁移、恢复和删除边界是否明确 |
| 平台 | 本地/远程能力、文件、密钥、资源、离线和分发路径是否可用 |
| 联动 | 同一角色、关系、事件和事实能否在多入口保持一致 |
| 维护 | 版本、兼容、回滚、测试和长期内容扩展是否可承受 |

### 3. 用最小证据消除高风险假设

对会改变架构的未知执行只验证关键问题的 spike，例如：一次模型调用、一个输出解码、一次保存重开、一个世界书触发或一个目标平台文件读写。不得把原型成功表述为全系统完成。

### 4. 形成完整设计

设计至少包含：目标与非目标、用户流程、内容契约、系统结构、权威状态、回合主链、错误恢复、安全、阶段切分和验收标准。简单项目可以合成一份短设计，但不能省略关键假设、非目标和完成标准。

### 5. 给出门建议

- `通过`：关键假设有证据，边界无实质矛盾，能拆成可验证切片。
- `有条件通过`：明确列出实施前必须满足的条件。
- `退回上游`：指出需修订的 owner 产物和原因。
- `暂停`：缺少用户授权、外部能力或无法安全处理的输入。

## 唯一产物

`Design Gate Package`：结构图、可行性证据、Host Capability Map、完整设计、风险、非目标、未决项和门建议。

使用 `../assets/templates/host-capability-map.md` 与 `../assets/templates/complete-design.md`。

## 轻量路径与升级

- 单一小功能：保留一页结构、假设、影响面和完成标准。
- 涉及状态权威、多模型、跨平台、导入执行代码、模式隔离或不可逆数据时升级完整方法。

## 交接与验证

- 通过后交给 `workflow-stages-delivery-and-change-control.md`。
- 质量分册验证假设和行为，不能替本册改变阶段。
- 检查每个系统有 owner、每个高风险假设有证据、每个失败有停止或恢复路径。

## 不负责

不修改 Gate State，不实施代码，不替领域分册定义内容规则，不把路线图写成逐文件计划。
