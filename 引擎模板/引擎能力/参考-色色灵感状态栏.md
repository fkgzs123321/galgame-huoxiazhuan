# 参考分析：`色色灵感状态栏V3.738`

> 来源：`C:\Users\64806\Downloads\-V3.738.json`（4.9 MB，酒馆助手脚本，不是角色卡）
> 规模：**458 条玩法 + 666 条成就 + 19 张数据库表**，玩法按选注入（不是全局挂载）
>
> 它跟我们**不是一套技术栈**（它用「数据库表 + SQL 指令」，我们用「MVU 变量 + zod + 引擎层 EJS」），
> 但有三处设计值得直接吸收。

---

## 一、它的核心范式：**数据库表 = 列定义 + DDL + 五个更新节点**

每张表的形状（以「主角技能表」为例）：

```js
{
  uid: 'sheet_protagonist_skills',
  name: '主角技能表',
  sourceData: {
    note:       '记录主角获得的所有技能…【列定义】列1: 技能名称 skill_name（全表唯一）…',
    ddl:        'CREATE TABLE zhujuejinengbiao (row_id INTEGER PRIMARY KEY, skill_name TEXT NOT NULL UNIQUE, skill_exp INTEGER NOT NULL DEFAULT 0 CHECK(skill_exp >= 0), …);',
    content:    [['row_id','技能名称','技能类别','技能经验值','技能描述']],
    initNode:   '游戏初始化时，根据设定为主角添加初始技能。初始技能经验值为0，描述10-50字。',
    insertNode: '禁止新增。',
    updateNode: '仅允许给技能经验值 +1~5。按触发强度：轻微 +1、常规 +2~3、关键 +4~5。★ SQL 示例(UPDATE …)。禁止修改其他列',
    deleteNode: '禁止删除。',
  }
}
```

### ★ 值得吸收的三点

**① 五节点把「AI 的权限边界」写死了**
`init / insert / update / delete` 四个动作**逐个写明允许做什么、禁止做什么**，而且
**`updateNode` 里直接给 SQL 示例**。

对照我们：我们的 `变量更新规则.yaml` 只写了「谁写、怎么算」，**没有逐动作划边界**。
→ 该在契约层给每张表补上这四个节点的说明。

**② DDL 里带 CHECK 约束**
`skill_exp INTEGER NOT NULL DEFAULT 0 CHECK(skill_exp >= 0)`
—— 约束写在**数据结构**里，不只写在提示词里。

对照我们：我们有 zod schema（等价物）✅ 这一点我们是对的。
但我们的合约层 yaml**没有把约束写进去**，只在 schema.ts 里。可考虑两边都标。

**③ 「基础形态」与「强化形态」分离**
它的原话（主角技能表）：
> 技能描述 skill_desc（10-50 字，描述技能作用；**激活天赋树后强化形态不回写本表**，
> 本表描述始终保持基础形态供技能识别与经验值累计，**强化形态由派生常亮条目「主角当前技能」注入世界书**；
> 不得自行改写本表描述）

★ **这条极其重要**：**表存基础，派生条目注强化**。
好处是「基础值永远不会被 AI 改坏」—— 哪怕强化算错了，底层数据是干净的。

对照我们：我们的 `强化()` 直接算加成，**没有「不回写基础」的约束**。
→ 该在物品表/技能表上写死这条。

## 二、它的天赋树是**玩家花钱改的树**

从脚本里挖到的实现（片段）：

```js
async function je(e, t) {
  const n = 取天赋树(e);
  if (!n) return { ok: false, reason: '无天赋树' };
  const r = 校验改动(n, t);          // ← 先校验
  if (!r.ok) return r;
  const a = await 算费用(e, 增量(n)); // ← 再算费用
  if (!a.ok) return { ok: false, reason: a.reason };
  const o = r.tree;
  o.editOperationCount = n.editOperationCount + 1;   // ← 记改了几次
  if (!await 保存(o)) return await 退费(e, a.costExp, a.costSerse), { ok: false, reason: '保存天赋树失败，费用已退回' };
  return { ok: true, costExp: a.costExp, costSerse: a.costSerse, operationCount: o.editOperationCount };
}
```

**树节点带 `parentId` / `tier` / `kind`** —— 是一棵真·树，不是列表。

### ★ 三件我们 C6 缺的事
1. **改图要付代价**（`costExp` + 另一种资源）
2. **要记改动次数**（`editOperationCount`）—— 改得越多越贵，或作为统计
3. **保存失败要退费**（`保存天赋树失败，费用已退回`）

★ 第 3 条是**事务意识**：**不能出现「扣了钱但没改成功」**。
对照我们：我们的 `付代价` 是先扣后做，**没做失败的回滚**。
→ C6 补「改图」时要带上「先校验 → 再扣 → 保存失败则退回」。

用户说的「**还能自定义生成**」指的就是这个 —— **玩家能自己改这棵树，而且是有代价的改**。

## 三、它的「检定建议表」跟我们的「出招层」是同构的

它的 `sheet_bwxtt33d5`（检定建议表）：
> 每轮根据最新剧情生成 5 条行动选项及对应的检定难度。全表固定 5 行，禁止新增或删除。
> 列1 展示文本 / 列2 检定难度（0-5）/ 列3 成功发展 / 列4 失败发展
> ★ 展示文本**禁止写「检定」「判定」等出戏词**

对照我们的出招层：`局面.当前选项` = 4 条（**固定四条**）+ 等级 + 感觉。
**同一个设计**（都是「她摆出若干条带难度的选项」），只是它 5 条、我们 4 条。

★ 它多了一样我们没有的：**每条选项预先写好了「成功发展」与「失败发展」**。
我们的判定结果只给「顶住了 / 没顶住」，**接下来发生什么要靠 AI 现编**。
→ 值得借鉴：**让选项自带两种走向**，判定完之后 AI 直接照那条走，不用自创。

## 四、明确**不**吸收的

| 它的做法 | 为什么不跟 |
|---|---|
| 用「数据库表 + SQL 指令」组织状态 | 我们已有 **MVU + zod schema**（等价且更严：zod 能校验结构，SQL 表不能）。**换栈没有收益** |
| 玩法按选注入世界书（458 条） | 我们是**条目按关键词触发**，机制不同；它的「按选注入」是为了解决「世界书太大」，我们的 selective 已经解决 |
| 主题皮肤（ancient / sweet / xianxia / bridge / ios 六套） | 面板皮肤是**面板层**的事，与引擎层无关。可以参考它的做法（同一份数据换套 CSS），但目前不必 |
| 666 条成就 | 那是**内容量**，不是能力。我们没有成就引擎（可以加，但不是引擎层缺口 —— 见下） |

★ 顺带记一个可能的缺口：**成就系统**。它 666 条成就，说明这是个**真需求**。
判据：换底座成立（任何游戏都有成就）／不含内容（成就是内容，但「解锁 + 统计 + 奖励」是能力）。
→ 可以进候选清单，但通用面比 E13/E14 窄。

## 五、吸收计划

| 补什么 | 落哪层 | 优先级 |
|---|---|---|
| **C6 补「改图」**：改要付费 + 记次数 + 失败退费 | 引擎层 | ★★★（用户点名的「自定义生成」） |
| **技能/物品：基础形态与强化形态分离** | 契约层写明 + 引擎的 `强化` 不改基础 | ★★★ |
| **契约层补「四节点」**（init/insert/update/delete 边界） | 契约层 | ★★ |
| **选项自带成功/失败两种走向** | 出招层 + 判定结果 | ★★ |
| 成就引擎（E16） | 引擎层（候选） | ★ |
