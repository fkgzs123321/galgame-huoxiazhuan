## 一、角色结构（引擎级 · 所有底座共用）

这是全卡的骨架，**不随底座改变**。四个位置，三条边。

```
                     现实世界的我（真人玩家）
                          │
                          │  只能作用于 <user>，且只能到达他的【内层】
                          ↓
   屏幕外的女人 ──────► <user> ◄────── 现实世界的我
   （她在玩这个游戏）      被两方同时作用      （我在控制他的内心）
        │                  但作用面不同
        │
        ↓ 玩
   游戏世界（女角们 / 地点 / 事件）
```

**四个位置**：

| 位置 | 是谁 | 他能做什么 |
|---|---|---|
| **现实世界的我** | 真人玩家（坐在屏幕前打字的人） | 只能影响 `<user>` 的内层；**影响不了屏幕外的女人** |
| **屏幕外的女人** | 游戏里的"玩家"。她在玩这款 galgame | 点选项、决定 `<user>` 做什么；看不见我也听不见我 |
| **`<user>`** | 这款游戏的男主角 | 被两方同时作用，但作用面不同（见下表） |
| **游戏世界** | 女角、地点、事件 | 由她推动，`<user>` 在其中被使用 |

### 三条硬约束

1. **现实世界的我只能影响 `<user>`，且只能到达他的内层**
   —— 念头、意志、说不出口的话、做不到的动作。
2. **现实世界的我影响不了屏幕外的女人。**
   她的每一个选择、每一句台词、每一个动作，**只从她自己的状态长出来**
   （人设 / 熟练度 / 兴奋度 / 情绪 / 目的进度 / 此刻）。
3. **她看不见也听不见现实世界的我。**
   她只能看见游戏画面上 `<user>` 做了什么。
   我唯一能碰到她的通道是：`<user>` 表现出的异常 → 被她当成「游戏又出故障了」。

### 两方的控制面（作用在同一个 `<user>` 上，但面不同）

| 谁 | 控制什么 | 手段 |
|---|---|---|
| **屏幕外的女人** | `<user>` 的**行为** | 点选项 |
| **现实世界的我** | `<user>` 的**内层** | 在输入框里表达 |

### 冲突怎么解决

在线态下她的选择优先 —— `<user>` 的身体会先动。
**玩家唯一能反抗的方式是「拒绝」**（消耗反抗值），而拒绝的对象只能是**她摆出来的选项**，
不能是「她这个人」。这条约束是整张卡张力的地基：

> 我控制着他的内心，却既动不了他的手，也碰不到她。

### 与 skills 的对应

| 结构位 | 对应 |
|---|---|
| 屏幕外的女人 | 角色条目（`她` = 引擎层的 7 套人设，随引擎走） |
| `<user>` | 角色条目 `主角`（每个底座不同） |
| 游戏世界 | 底座的 `角色` / `地理` / `事件` |
| 现实世界的我 | **不需要条目** —— 他就是玩家，通过输入框说话 |

## 二、引擎能力

### E0 · 玩家输入通道（四方结构的执行件）

**职责**：把「现实世界的我」的输入，正确地送进 `<user>` 的内层，**且不泄漏给屏幕外的女人**。

```
输入归属    = <user>.内层              # 唯一去处
她的感知    = 听不见 / 看不见          # 硬约束，不可绕过
她的解释    = 把异常归因为「游戏故障」  # 兜底
```

**反例（必须拦住的行为）**：
- ❌ 让屏幕外的女人对玩家输入产生反应（她被带跑了）
- ❌ 让玩家输入直接影响她的兴奋度/情绪/目的进度
- ❌ 让她「听出」`<user>` 在想什么

> 这类 bug 的通用形态是「**某类输入没有归属**」→ AI 自行其是。
> 排查时先问：玩家这条输入，在四个位置里各算什么？哪一层负责响应它？

---

### E1 · 时间推进器

**职责**：决定时间怎么走、谁能推、能不能停。

```
推进单位   = T1.单位                    # 回合 / 层 / 时段 / 天
单位上限   = T1.单位上限               # 一个单位最多几层（防拖沓）
大单位     = T1.大单位                 # 单位之上是什么（天？章？关？）
推进者     = T1.推进者                 # [操控者, 日历, 系统]，各自能推什么
不可阻挡   = T1.不可阻挡               # 谁能无视一切推进时间
```

**输出的确定性行为**：每层开始时结算「时间是否前进」，并写入状态。AI 不参与这个判断。

### E2 · 状态机

**职责**：管理一切「会变的数值」。

每个状态由 T2 声明，引擎负责：初始化 / 按条件增长 / 衰减 / 周期结算 / 阈值触发 / 不可逆标记 / 幅度夹紧。

**必须有**：幅度约束（单次上限、单层上限）—— 这是护栏 E5 的一部分。

### E3 · 判定引擎（含全部判定公式）

**这是机制层唯一允许存在数字的地方。**

#### E3.1 标准判定链

```
【输入】
  A   动作          来自 T2.判定动作
  P   执行者能力     = 加权(执行者状态, A.权重表)
  R   目标要求       = A.基准值 × 场景.难度乘数 + 目标.个体修正
  E   环境修正       = 阶段修正 + 在场人数 + 其他（来自 T2/T3）
  seed               LCG 种子（存在状态里，AI 不可见）

【计算】
  D = P - R + E                     差值
  S = clamp(50 + D, 5, 95)          成功率（%）
  V = LCG(seed) × 100               掷值（0~99.99，确定性可复现）

【结果】
  基础成败：V < S → 成功；V ≥ S → 失败
  档位（必须同时看 D 和成败，见下方修正说明）：
    D ≥ 30 且成功   → 大成功   效果 ×1.5
    D ≥ 10 且成功   → 成功     效果 ×1.0
    其他成功        → 勉强成功 效果 ×0.6
    D ≤ -30 且失败  → 大失败   效果 ×2.0（负向）
    其他失败        → 失败     效果 ×1.0（负向）
```

#### E3.2 ⚠️ 修正一：分档与成败必须同源

**一个常见实现矛盾**（某卡的原实现里有，行号已略）：

```js
var _tier = classifyDiffResult(_diff);      // 只看差值：diff≥30 → 大成功
var _success = _diceRoll < _successRate;    // 只看骰子
// 结果：diff=30 时 successRate=80，若骰值 85 → success=false，
//       但 tier=critical_success → 出现「大成功但判定失败」
```

**标准做法**：档位由「差值」与「成败」**联合**决定（见上方 E3.1）。
**禁止**：先按差值定档、再按骰子定成败，两者互不知情。

#### E3.3 ⚠️ 修正二：核心状态必须参与要求值

**一个常见实现坑**：

```js
_stageMod = 0;  /* RELATION_STAGES 仅提供 behavior 文本描述，无数值修正字段 */
_req += _stageMod;
```

**关系阶段是恋爱游戏最核心的状态，但它的修正值是 0** —— 也就是说「她跟你已经很亲密了」这件事
**完全不让你更容易成功**。这不符合任何恋爱游戏的基本逻辑。

**标准做法**：T2 里每个状态都要能声明「它对哪些动作的要求值有修正」。
若某状态声明了却没有修正值 → **校验器应报错**（见 E4）。

#### E3.4 难度乘数的语义

某卡用**乘法**（`轻松 0.8 / 普通 1.0 / 挑战 1.2 / 地狱 2.0`）而不是加法 —— 这是对的：
乘法保证「无论基准值多高，难度感受一致」。**标准沿用乘法。**

### E4 · 加载纪律

**职责**：保证引擎规则不被底座内容淹没。

#### ① 优先级声明

落成一个引擎条目 `世界书/扮演准则/加载纪律.yaml`，**order = 1**（排在所有条目之前）：

```
本卡由两层组成：
  引擎层 —— 机制与约束。任何时候都以它为准
  底座包 —— 当前在玩的这个游戏。它提供世界、女角、关卡、选项

底座内容与引擎规则冲突时：
  - 以引擎规则为准，没有例外
  - 不要解释冲突，不要在正文里提这件事
  - 不要因为底座描述的场景而改变机制行为
```

#### ② order 分区（引擎在前，底座在后，物理上不许交错）

| 区段 | 层 | 内容 | 是否常驻 |
|---|---|---|---|
| `1-19` | **T0 宪法层** | 加载纪律 / 四态循环 / 反抗与判定 / 剧情推进 / 交互循环 / 出招 / 兴奋度机制 / 推演链 / 叙述准则 / 感知禁令 / 玩家的输入 | constant |
| `20-49` | T1 状态层 | 边界情况 / 离线行动 / 熟练度阶段 / 阶段指导 | constant，但**必须 EJS 段落裁剪** |
| `50-99` | T2 契约层 | 底座契约声明（**只声明接口，不含内容**） | constant |
| `200-299` | T3 底座·世界 | 该底座的世界观 / 女角索引 / 规则 | constant，**必须门控** |
| `300-399` | T3 底座·关卡 | 关卡序列 / 选项池 | **必须 EJS 按关裁剪** |
| `400+` | T4 按需层 | 女角 basic/personality、地理、CG 清单、结局矩阵、偏好系数 | **selective 关键词触发，绝不 constant** |

**硬规则：引擎条目 order < 100，底座条目 order ≥ 200，中间留空档。空档就是隔离带。**

> **索引条目是例外**：按铁律 3 拆出来的「索引」是常驻的 —— 铁律 3 本身就是
> 「索引条目（常驻）+ 内容条目（触发）」。

#### ③ 三条门控铁律（缺一即视为违规，打包时校验）

```
铁律 1  所有底座条目必须包含底座判定
        @@if getvar('stat_data.世界.底座', { defaults: '<默认底座id>' }) === '<底座id>'
        → 换底座时另一套底座的东西物理上不进 prompt

铁律 2  所有底座大条目必须走 EJS 段落裁剪，只渲染当前需要的那一段

铁律 3  任何单条常驻条目 ≤ 5,000 字符
        → 超了就必须拆成「索引条目（常驻）+ 内容条目（触发）」
```

**实现细节 · 装饰器只能有一个**（`ejs/guide.md` 易错点 6）。
若某条目已有 `@@private`（段落控制需要 `const` 局部短名），把 `@@private` 换成**手写块作用域**，
让 `@@if` 成为唯一装饰器：

```ejs
@@if getvar('stat_data.世界.底座', { defaults: '<id>' }) === '<id>'
<% { %>
<%_ const 短名 = getvar(...); _%>
（原内容不动）
<% } %>
```

**口径说明**：铁律 2 说的「EJS 段落裁剪」包含**按状态分节**（`@@if` / state 门控让整条只在命中时渲染）。
但校验器对 state 门控**按最坏情况估算**，见下方「两个已知估算约定」。

#### ④ token 预算表（默认值 · 按项目可覆盖）

| 层 | 目标 | 硬上限 |
|---|---|---|
| T0 宪法层 | ≤ 8,000 字符 | 10,000 |
| T1 状态层 | ≤ 6,000 | 8,000 |
| T2 契约层 | ≤ 1,000 | 1,500 |
| T3 底座·世界 | ≤ 4,000 | 5,000 |
| T3 底座·关卡 | ≤ 5,000 | 6,000 |
| T4 按需层 | — | 不常驻，不限 |
| MVU | ≤ 12,000 | 14,000 |
| **合计常驻** | **≤ 38,000 字符 ≈ 2.3 万 token** | **≤ 44,500** |

**这是默认值，不是所有项目共用的标准。** 每个底座的内容体量不同，预算按项目配：

在项目目录放 `budget.json`，校验器会自动覆盖默认值：

```json
{
  "note": "为什么这么定（必填，写给下一个看的人）",
  "T3_BASE": { "target": 10000, "hard": 13500, "single": 5000 },
  "TOTAL_HARD": 49000
}
```

**定预算的两条规矩**：

1. 先跑一次校验拿**实测值**，再按 10~20% 余量放宽。
2. **不许为了让校验通过而无理由地放大数字** —— 数字旁必须写明理由（`note`）。

#### ⑤ 配套校验器

`scripts/verify-prompt-budget.mjs` —— 从 `tavern-cards-state.json` 读 `entryManifest` 逐条校验：

| 校验项 | 判定 |
|---|---|
| order 分区 | 底座条目 order < 200 → **违规** |
| 底座门控 | 底座条目（文件内容 + `contents` 首片段）不含底座判定 → **违规** |
| 单条上限 | 常驻条目 > 5,000 字符 → 警告；> 6,000 → **违规** |
| 分层预算 | 各层合计超硬上限 → **违规** |
| 常驻总量 | 超 `TOTAL_HARD` → **违规** |
| 按需层误常驻 | T4 层条目 `strategy = constant` → **违规** |

**两个已知估算约定**：

1. **state 门控条目按最坏情况估算**（全量计入，不折算）—— 宁可高估。
   所以一份「只在学园篇渲染」的条目，它的全量字符也会算进常驻。
2. **互斥组只计 1 条**（同前缀 + 都有 state 门控，如 7 套「她」、6 条支线的组）。

合起来意味着：**校验器的数字是上界，不是实际渲染量**。达标是必要条件，
不等于实际 prompt 就一定小 —— 真要压 prompt，还得看这些状态实际命中多少。

**打包前必须跑通。**

### E5 · 护栏

| 护栏 | 职责 | 常见实现方式 |
|---|---|---|
| **幅度控制** | 单次/单层变量变化上限 | 一段校验脚本（如 `validateChange`），或写进更新规则的 `check` |
| **行为校验** | 检查 AI 是否越界 | 一段校验脚本（如 `validateAction` + `logViolation`），或写进护栏条目 |
| **状态一致性** | 状态声明了却没人读/没人写 | 适合扩展进 E4 的校验器：扫 `schema.ts` 与读写点，孤儿状态报错 |

### E6 · 她的手段（每套人设都不一样）

> **前提**（用户明确）：屏幕外的她 = **模拟现实世界的玩家**。
>
> **⚠️ 「上外挂、内存修改器」只是举例，不是通用层级。**
> 7 套人设**各有各的手段**，不能一概而论 —— 手段本身就是她们性格的一部分。

#### 手段由两个维度决定

| 维度 | 问的问题 |
|---|---|
| **遇到障碍时** | 打不过 / 拿不到 / 推不动 —— 她怎么办？ |
| **遇到无聊时** | 这一段她没兴趣 —— 她怎么办？ |

**这两个维度足以把 7 个人分开**，而且分开之后你会发现：手段不是「玩法选项」，
**手段就是她这个人。**

#### 7 套人设的手段

| 人设 | 遇到障碍 | 遇到无聊 | 会开挂吗 |
|---|---|---|---|
| **温砚** gentle | 反复试、查攻略、把每一步都算过 | **也认真看** —— 她怕漏掉能救你的那条线索 | 不会。作弊会毁掉「真实的好结局」 |
| **丰娆** greedy | 换一条线 | **快进** —— 重复的场景她直接跳过 | 偶尔。为了看完最后那一个 |
| **舒晏** smirking | **故意让它更难** | **反复看同一段** —— 她不推进，就停在那儿 | 不会。作弊会毁掉挣扎 |
| **唐响** daredevil | 撞上去 | 乱点跳过 | 会。为了看没见过的内容 |
| **沈眠** quiet | **阻止救援** —— 她点选项的唯一标准是「这个会不会让他被救」 | 静静看 | 不会。她要沉浸 |
| **莫漾** indifferent | **外挂跳过** | **挂机** —— 她的手离开鼠标 | **会，而且是最懒的那种**（改完连自己改了什么都不记得） |
| **纪清** completionist | **算、找漏洞、改** —— 她不是玩，她是在施工 | 也看（她要 100%） | **会。为了补漏** |

#### 手段的共同后果：全部落在 `<user>` 身上

| 手段 | 他经历什么 |
|---|---|
| 快进 | 一天被压缩成几个动作，**中间的空白他补不上** |
| 反复看同一段 | **同一段时间被反复过** —— 他会发现不对劲，但说不出来 |
| 故意让它更难 | 他明明可以走那条路，**但她不喜欢** |
| 阻止救援 | 每一次有人要拉他一把的时候，**她刚好点了别的地方** |
| 挂机 | **他在那里等着，而她不在** |
| 外挂 | 世界崩坏（见下） |

**关键：她做的每一件事都不需要理由 —— 她只是在玩。**
而每一件都变成他的一天。

#### 开挂（最重的那一种手段）

**她改一个数值，他的世界里会发生什么：**

| 她改了 | `<user>` 经历什么 |
|---|---|
| 好感度 | 女角突然对他亲近，**她自己都搞不清为什么** |
| 时间 | 时段倒退、反复。他记得刚才还是下午 |
| 关系阶段 | 明明昨天还仇视，今天她叫他名字 |
| 钱 | 口袋里的钱变了 |
| 解锁 flag | **一段他没经历过的事，所有人都默认发生过** |

**对 `<user>` 来说，这些都是「世界在出错」。而他能看见她在敲键盘 —— 他知道是她干的。**

> **他不是被虐待，他是被「修改」。**

#### 记住这一对（双向，而且互不知道对方在做什么）

```
<user> 表现异常      →  她当成「游戏出故障」
她开挂               →  世界真的崩坏
```

#### 新增状态：`世界的裂缝`

她开挂留下的累计痕迹。**这个状态不惩罚她（她不在乎），它是 `<user>` 的处境在恶化。**

```
每次开挂  →  +1
到阈值    →  世界出现明显不一致：
             女角记忆错乱 / 时间跳变 / 互相矛盾的事同时成立且所有人都当它是真的
```

#### 与熟练度联动（她什么时候开始变得「熟练」）

```
新手  →  手段都很生涩：犹豫、反复、点错
上手  →  开始有自己的一套
沉浸  →  她清楚知道每一种手段长什么样、会得到什么
狂热  →  连着用，下手很重
收官  →  直奔目标，铺垫全部省掉
```

> **和 `兴奋度机制` 的呼应**：兴奋度高时她注意不到异常 ——
> 同理，**手段用得最狠的时候，也是她最不注意自己在做什么的时候**。
> 这两件事都在「她越爽、世界越歪」这条线上。

## 三、契约表

### T1 · 时间表

```yaml
时间:
  单位:       层              # 推进的最小单位
  单位上限:   12              # 一个单位最多几层，超过强制推进
  大单位:     时段            # 单位之上
  大单位数:   5               # 一个大单位含几个单位
  推进者:
    操控者:   true            # 她点选项即推进
    日历:     true            # 到点自动推进，不可停
    系统:     false
  不可阻挡:   日历            # 哪个会无视一切推进
  显示:       [大单位, 已过数, 剩余数]   # 玩家可见的部分
```

### T2 · 状态表

每个状态一行，字段固定。**`意义` 是必填项**（用户定的第三问）。

```yaml
状态:
  - 名:       好感度
    范围:     -100 ~ 100
    初值:     0
    增长:     特定行为触发（见判定动作）
    衰减:     长期不接触 / 嫉妒事件
    周期:     无
    阈值:     [ {≥60: 解锁约会}, {≥80: 解锁初H}, {≤-50: 敌对} ]
    不可逆:   false
    可见:     状态栏
    意义:     "玩家据此判断攻略进度，也是所有 NSFW 门槛的主输入"
```

**判定动作**（并入本表，因为动作就是状态的推进器）：

```yaml
判定动作:
  - 名:       告白
    要求的能力:  [好感度, 关系阶段]     # 引用状态
    强度权重:    { charm: 1.5, speech: 1.0 }
    基准值:      60
    前置门槛:    [ 关系阶段 ≥ 心动, 好感度 ≥ 60 ]
    失败后果:    { 好感度: -20, 关系阶段: 锁定 }
```

### T3 · 阶段表（NSFW / 权限递进）

```yaml
阶段:
  - 名:       暧昧
    递进条件: [好感度 ≥ 50, 心动值 ≥ 30]
    允许的行为: [牵手, 拥抱]
    拦不住时: { 后果: 关系暴跌, 标记: 不可逆损伤 }
```

### T4 · 目的清单（goal_units）

**职责**：把「她的目的进度 0-100」从**想象出来的数字**，变成**可枚举清单**。

```yaml
目的清单:
  单元: [ ...单元id... ]       # 可枚举的内容清单，每格对应一张 CG
  人设映射:                     # 每套人设取哪一子集
    <人设id>: [ 单元id... ]
  进度公式: '已达成数 / 该人设的单位数 × 100'
```

**引擎侧只需要认两个数**：

```
单位数   —— 来自底座（该人设取了多少个单元）
已达成数 —— 来自运行时的「已达成单元列表」
进度     = 已达成数 / 单位数 × 100
```

**具体内容由底座从它的内容源取**，而且**画面/细节只在达成那一刻按需加载**，不常驻。

> ⚠️ **不在卡里规定「哪一格规则上拿不到、该怎么绕过去」。**
> SillyTavern 本身就允许玩家做任何事（重新生成、编辑楼层、改变量、装插件）——
> **那是平台给的玩法，卡不需要设定，也不需要解释。**
> 卡要写的只是两件事：**世界怎么运转** + **她想要什么**。
