# 欲望都市 · Token 爆炸分析报告（只分析，未改动任何内容）

> 目的：在**不改任何机制描述/人物叙述细节**的前提下，定位"开局 8 万、两三楼 12 万 token"的来源，给出配置层优化方案。
> 数据来源：`tavern-cards-state.json`（注入配置）+ `欲望都市.png` ccv3（打包后真实 content/keys/enabled）+ EJS 实测输出。

| 来源 | 体积 | tokens | 占比 | 说明 |

## 二、你的三个问题的直接回答

### Q1：是 EJS 没做好"全量拉取"吗？—— 不是

EJS 条目实测输出（Node 执行验证）：

| EJS 条目 | 无目标（开局） | 有目标（战斗） |
|----------|---------------|----------------|
| 情境上下文EJS | 687B ≈ 172 tokens | 607B ≈ 152 tokens |
| 阶段调度 | 196B ≈ 49 tokens | 253B ≈ 63 tokens |

- EJS 本身**输出极小**，getwi 是标准"按需拉取"：无战斗目标时一行不拉，有目标才拉当前角色——完全符合规范（参考卡"不要玩弄我的鸡吧"、同级生2 同款"关灯+getwi"架构）。
- **唯一可议点**：进入战斗后，阶段调度**每次战斗都全量 getwi 癖好标签库（6.3KB）+ 性格标签库（3.2KB）**，约 2.4K tokens/轮。是小头，可拆分优化（非必须）。

### Q2：是关键字没对齐吗？—— 恰恰相反，是"对齐得太彻底"

- 38 条基础信息 keys = 角色名（如 `林汐瑶`），设计初衷（名录总表注释原文）：*"基础信息为绿灯（提到名字由酒馆原生注入）"*——本意是"同场角色才注入在场者"。
- **但 first_mes 开场白提到了全部 38 个角色名（38/38 全命中）**。ST 的 selective 机制扫描聊天历史（first_mes 是第一条助手消息），于是**开局 38 条全部激活**，22.6K tokens 从"按需"实际变成了"常驻"。
- 后果：卡静态注入一半被"永远不会同时出场的人设"占据；且 AI 回复每提到一个新名字还会继续激活新条目，历史越长叠加越多。
- 附注：getwi 名称对齐基本 OK（`X_私密档案`/`X_阶段行为` 与打包后条目名匹配）；仅 `getwi(tgt + '_性格与癖好')` 指向不存在的条目，拉空一次，无害但浪费一次调用。

### Q3：哪些没必要每轮全量录入？—— 头号就是 38 条基础信息

- **38 条角色基础信息（22.6K）**：名录总表（1.3K 蓝灯索引）已承担"谁是谁"的速览职责，基础信息详情完全没必要开局全量注入。
- first_mes 37KB（9.3K）：属叙事内容，按你的要求不动（可在 ST 侧用历史压缩缓解）。
- constant 18 条（9.5K）：都是核心规则，但"道具/战斗系统/生理"属战斗类规则，可评估场景化（非战斗时不注入）——改动较大，需你决定。

## 三、优化方案（全部只改激活配置，内容一字不动）

### 方案 A（推荐，收益最大、零内容改动、风险最低）

**38 条基础信息从"绿灯（selective）"改为"关灯 + getwi 按需"**，与私密档案同一套机制：

1. state 中 38 条 `X_基础信息`：`enabled: true` → `false`（关灯，不参与关键词激活）
2. `阶段调度.yaml` 的 getwi 序列增加一行：`<%- await getwi(tgt + '_基础信息') %>`（有战斗目标才拉当前角色详情）
3. 名录总表保持蓝灯常驻（已是索引，不动）

**收益**：
- 开局：-22.6K tokens（卡静态 41.6K → **19K**，降 54%）
- 战斗时：仅 +当前目标基础信息 ~2.5K（与原来同场 2~3 条激活 5~7K 相比反而更省）
- 多角色同场：原来"在场 2 人 → 2 条全激活 5K"，现在只拉当前目标 1 条 2.5K

> 注意：方案 A 的依据**只来自 skills 规范**（tavern-cards EJS 参考 + STDB），不引用任何其他卡的做法。规范依据见下文"五、skills 规范研判"。

### 方案 B（可选，小收益）

癖好标签库/性格标签库拆分：由"每次战斗全量拉 9.5K"改为按缴械值阶段拉对应子集。收益 ~2.4K tokens/轮（仅战斗轮）。

### 方案 A'（替代：scan_depth 限制扫描范围，保留原生关键词激活）

- 依据：`tavern-cards/references/configuration.md` 定义 `strategy.scan_depth`（`"same_as_global"` 或数字，扫描最近几条消息）
- 做法：38 条基础信息 `strategy.scan_depth = 2~3`，内容零改动
- 效果：**渐进式缓解**——历史短时 first_mes（第 1 条）仍在扫描范围内，开局前几楼仍会激活；历史增长后 first_mes 移出扫描范围，只激活近期提到的角色
- 结论：不能根治开局 8 万，适合作为"保留原生激活 + 控制误激活"的折中

### 方案 C（可选，改动较大）

constant 中的战斗类规则（道具 4.7K + 战斗系统 4.3K + 生理 3.9K ≈ 12.9K tokens）改场景控制器式加载：非战斗时段不注入，进入战斗时按条件 getwi 拉取（`@@generate_before` + `if(条件) print(await getwi(...))` 是 EJS 规范的标准用法，见 tavern-cards `references/ejs/features.md` "Using getwi to Directly Load World Book Content"）。收益 ~12.9K tokens/轮，但需新增控制器逻辑，风险较高，建议单独评估。

### 环境侧排查（非卡可控，但影响观感数字）

- ST 预设系统提示大小（换轻量预设可省 1~3K）
- ST「聊天历史压缩」(Chat Compression) 是否开启——first_mes 9.3K 会被压缩
- 模型上下文窗口：若 8 万/12 万已接近上限，优先做方案 A
- 正则脚本 promptOnly 已确认正确（[0][1][2] 注入空、[3][4] 不注入）✅ 无额外开销
- ⚠️ **getwi 加载的内容不计入 ST 的 token 预算统计**（tavern-cards `references/ejs/features.md` §Context Token Budget）——getwi 实际消耗上下文但顶栏不显示，方案 A 后"显示数字"会大幅下降，但 getwi 拉取是隐藏消耗，拉取过多可能静默超限

## 五、skills 规范研判："基础信息全关 + getwi 拉取"能实现吗？

> 本研判**只引用 skills 规范**（tavern-cards + STDB），不参考任何其他角色卡。

### 结论：能实现，且是 skills 规范支持的标准做法

| 规范条款 | 内容 | 对方案 A 的意义 |
|----------|------|-----------------|
| tavern-cards `ejs/features.md` §Using getwi to Directly Load World Book Content | getwi"完全绕过 SillyTavern 原生世界书激活逻辑，直接把指定条目加载进当前上下文（即使当前上下文不是世界书条目）"；"无条件激活"；"**可激活未挂载的世界书条目**" | getwi 按标题直读条目内容，**不受原生激活逻辑限制**——disabled 条目也可被 getwi 加载 |
| tavern-cards `ejs/features.md` §Using activewi | activewi"自动把 **disabled 条目当 enabled 处理**（不改动世界书本身），即禁用条目也能被激活" | 配套函数明确支持 disabled 条目 |
| tavern-cards `ejs/reference.md` getEnabledWorldInfoEntries | "**Even disabled entries are returned**（连禁用条目都会返回）" | 扩展的世界书读取接口明确包含 disabled |
| tavern-cards `configuration.md` §策略推导 | `null` → **禁用**（`enabled: false`）是合法的标准策略 | "关灯"是规范定义的策略，不是旁门左道 |
| tavern-cards `manual.md` §校验 | "[InitVar] 条目必须显式设置 `enabled: false`" | 本架构中控制类条目**规范要求关灯**，disabled + EJS 驱动是标准形态 |
| tavern-cards `configuration.md` §keywords | "selective 模式：关键词出现在**聊天历史**中时激活"；STDB A3 "每次生成前**扫描聊天历史**，关键词命中 → 注入" | 确认 38 条基础信息被 first_mes 全命中的判断——selective 匹配聊天历史 |
| tavern-cards `configuration.md` §scan_depth | `"same_as_global"` 或数字，扫描最近几条消息 | 方案 A' 的依据 |

### 两个必须遵守的规范警告

1. **getwi 内容不计入 ST token 预算**（features.md §Context Token Budget）："prompts imported using getwi, getvar, getchr... are not counted, which may also lead to exceeding the budget"。→ 方案 A 后 ST 显示数字会骤降，但 getwi 拉取是"隐藏消耗"；阶段调度每轮 getwi 拉取量需克制（建议：有目标时只拉 当前目标基础信息 + 私密档案，标签库改为条件拉取）。
2. **enabled=false 条目被 ST 原生完全忽略**（configuration.md §enabled）："false 时条目完全被忽略"。→ 关灯后 AI 上下文里**永远没有**该内容，必须有常驻索引兜底（名录总表 ✅ 已存在）且 getwi 必须在正确时机触发（阶段调度 ✅ 已有机制，补一行 `getwi(tgt + '_基础信息')` 即可）。

### 修正声明

上一版报告曾引用其他角色卡的架构做法（"不要玩弄我的鸡吧""同级生2"）作为方案依据——**该引用无效**，方案 A 的可行性仅以本节的 skills 规范条款为据。

## 四、结论一句话

**token 爆炸主源不是 EJS、不是关键字错位，而是"38 条角色基础信息的绿灯被 first_mes 全量点亮"（22.6K ≈ 54%）**。做方案 A 即可零内容改动砍掉一半静态注入；若再叠加方案 C，开局可压到 ~6K 量级。

## 六、癖好/性格的组织方式研判（skills 规范版）

> 问题：癖好和性格组合，该"分散到每一个人的条目里"还是"拆分到几十个独立癖好/性格条目由 getwi 拉取"？
> 依据：tavern-cards `references/composition.md`、`contents-creation/character/personality-palette.md`、`multi-stage.md`、`character-catalog.md`

### 结论：分散到每一个人（规范明确支持，且项目已有正确雏形）

**1. 性格 → 每人"阶段调色盘"（项目已合规）**
- `personality-palette.md`：调色盘按角色组织——底色 + 主色调 + 点缀 + **衍生**（"衍生写具体场景和行为，不写抽象定义"）
- `multi-stage.md`：阶段专属衍生 + 通用衍生
- 项目现状：每个角色的 `基础.yaml` 已有 `## 阶段调色盘`（如林汐瑶：底色"怕被落下"+通用衍生"嘴硬/不服输"）✅ 符合规范

**2. 癖好 → 并入个人条目（私密档案），而非全局标签库**
- `personality-palette.md` 原文："**衍生由用户自己写，AI 写的衍生永远逃不出资料库与逻辑的关联性，只有人才能把毫无关联的性格组合在一起**"——共享词典 = 资料库逻辑 = 角色同质化，规范明确反对
- "衍生写具体场景和行为，不写抽象定义"——标签库的"汗后兴奋/怕痒放大"是抽象标签名，缺场景行为
- 同标签跨角色（"汗后兴奋"同时挂在 林汐瑶/赵雪晴/陆青霞），共享定义会让她们表现雷同
- 正确落位：癖好的**组合 + 场景衍生**写进各自 `私密.yaml`（私密场景行为，与身体描写内聚），getwi(tgt + '_私密档案') 一次带出

**3. "拆分到几十个独立癖好/性格条目"不符合规范**
- 标签条目共享 → 同上同质化问题
- 拉取粒度错误：getwi 按"标签"拉，需先知道每人有哪些标签（映射表）→ 每人 2-4 个标签 = 2-4 次 getwi；而按"角色"拉 = 1 次 getwi 拿全
- 规范的组织单元是"角色"（per-role 调色盘），不是"标签"

### 当前实现的两个孤儿（方案落地前必修）

| 孤儿 | 位置 | 说明 |
|------|------|------|
| `getwi(tgt + '_性格与癖好')` | 阶段调度.yaml 第 11 行 | 指向**不存在的条目**，每次拉空（浪费一次调用） |
| 基础信息关灯后无 getwi 入口 | 方案 A 执行时 | 阶段调度注释"基础信息为绿灯，此处不重复拉取"——若基础信息改关灯而不补 `getwi(tgt + '_基础信息')`，基础信息将永远拉不到（孤儿） |

### 常驻索引（名录总表）补全

- `character-catalog.md`："角色速览是角色索引…**必须包含姓名、性别、年龄**"——名录总表现有 39 行（38 人 + <user>）全覆盖 ✅ 无孤儿，但行格式缺**性别/年龄**字段，按规范需补
- 排序要求"<user> 最前" ✅ 已满足

### 规范版完整落地路径（供你拍板，未执行）

1. **基础信息**：38 条 `enabled: false`（关灯）+ 阶段调度补 `getwi(tgt + '_基础信息')`
2. **癖好**：把"组合+场景衍生"从全局标签库迁入每人 `私密.yaml`（或保留标签库仅作速查索引，详细定义迁个人条目）
3. **阶段调度**：删 `getwi(tgt + '_性格与癖好')`（孤儿）；getwi 序列改为按角色精准拉：`_基础信息` + `_私密档案` + `_阶段行为`（+缴械值≥100 时 `俘虏结局`）
4. **名录总表**：补性别/年龄字段（内容零语义改动，纯补全）
