### 2.5 加点系统（**【读到】** `game-utils.js` L682–700）

`calculateRemainingPoints()` 是"反向工程"式设计——**不存"剩余点数"，而是从当前数值反推已用点数**：

```js
earnedLevels = calculateLevelFromWuxue(playerStats.武学)   // 武学→等级，最多30级
usedForAttack      = (攻击力 - 20) / 10
usedForHP          = (生命值 - 50) / 25
usedForCritRate    = (暴击率 - 10) / 15
usedForCritDamage  = (暴击伤害 - 150) / 20
usedForBlock       = (格挡 - 0) / 10
usedForArmorPen    = (穿甲 - 0) / 10
usedForLifesteal   = (吸血 - 0) / 15
usedForThorns      = (反伤 - 0) / 15
usedForTurnover    = (回转 - 0) / 0.1
remaining = round(earnedLevels - totalUsed)   // 且 Math.max(0, ...)
```

**优点**：不需要额外存字段，存档天然一致。
**坑**：装备加成必须**排除在外**（所以代码用 `combatStats` 而非 `getTotalCombatStats()`），且**只要有一个来源绕过这个换算直接改 `combatStats`，点数就会漂移**。`useItem()` 就用 `combatStats[attr] += value` 直接改（`game-helpers.js` L1276–1277），如果哪个道具带 `攻击力` 就会立刻污染点数系统 —— 好在通读 `item-list.js` 后确认**所有 `影响属性` 只出现 `playerMood` 和 4 项天赋**，没有战斗属性，暂时安全。

**等级换算**（L219–242）：`calculateLevelFromWuxue(wuxue)` 中第 i 级需要 `Math.ceil(2 + i/2)` 点武学，累加最多 30 级。

## 3. AI 与代码的边界

### 3.1 AI 是怎么被调用的（**【读到】**）

**核心机制：不是 `generate()`，而是 `/inject` + `/trigger`。**

`game-helpers.js` L130–131：

```js
await renderFunc(`/inject id=10 position=chat depth=0 scan=true role=user ${message}`);
await renderFunc('/trigger');
```

`special-event.js` L4687–4694 用同一套，但**多一步 `/sendas`**：

```js
await renderFunc(`/inject id=10 position=chat depth=0 scan=true role=user ${userMessage}`);
await renderFunc(`/sendas name={{char}} at={{lastMessageId}}+1 ${safeText}`);
```

**【读到】** 这里有一个明确的"先存后发"纪律：`handleMessageOutput` 在注入前 `await saveGameData()` 两次 + 两次 `setTimeout`（500ms / 100ms，L120–127），注释写"确保变量完全同步到 SillyTavern"。`triggerSpecialEvent` 里是同样的 500ms+100ms 模式（L4678–4684）。

**【读到】全项目未找到** `generate(`、`generateRaw(`、`TavernHelper.`、`getVariables(`、`replaceVariables(`、`eventOn(`、`tavern_events`、`getChatMessages(` 的任何调用。所有 ST 交互**只在 `triggerSlash` / `STscript` 这一条通道上**，形态是裸 STScript 字符串。

**边界结论（诚实版）**：

- ✅ **AI 完全不能碰的**：`playerTalents` / `playerStats` / `combatStats` / `playerMood` / `actionPoints` / `currentWeek` / `inventory` / `equipment` / `npcFavorability` 的**具体增量**。没有任何一条代码路径把 AI 输出的数字直接写进这些变量。
- ⚠️ **AI 仍然能间接影响的数值**：
  1. **好感度**：AI 选标签，代码换数字 —— **但 AI 决定了方向，且"大幅"档在 normal 难度下就翻倍**（+1 vs +2）
  2. **事件奖励**：`applyEventReward()` 的正则**直接从 AI 字符串里抠数字**（`悟性+3`）。虽然经过 `hasOwnProperty` 白名单 + `checkAllValueRanges()` 夹紧，但 **+3 还是 +300 完全由 AI 决定**（上限 100/300 兜底）
  3. **成功率**：`parseInt` 后直接当概率用，**AI 可以写 100%**
  4. **战斗奖励**：`applyBattleReward()` 用 AI 给的 `数值`。**但悬赏战斗例外** —— `game-events.js` L902 有明确注释："悬赏战斗结算：奖励来源固定为 activeBounty（**不信任 SIDENOTE 里 LLM 自行编造的数值**）"，L616–627、L659–677 还做了两层兜底
  5. **掉落稀有度**：AI 给的 `武学` 0–9 直接决定 `rollRarityByPower()` 的区间（L280–314）

所以准确的说法是：**主线数值（属性/战斗/资源）由代码垄断；支线数值（随机事件奖励、成功率、战斗报酬、掉落档位）仍是"AI 提名、代码盖章"。**

### 3.5 邮件 / 事件 / 行动分别怎么触发 AI

- **邮件**：**【未找到】**。全项目 grep `邮件|mail|书信|飞鸽` 只命中 4 处，全是剧情文本里的"书信"道具描写（`special-event.js` L941/L1810/L1822）和 `attributeTierDescriptions` 里的学识描述（`game-config.js` L147）。**这张卡没有邮件系统**。

### 7.1 结构（**【读到】** 191 行）

L1           <!-- <UserInfo> is the information of user {{user}} -->   ← 给世界书/人看的注释

### 7.3 写作风格特征

**① 三段式结构：说明 → 定义 → 当前水平**

每项属性固定三行，先给 AI 一个"这个属性是干什么的"（定义），再给"你现在处于什么位置"（当前水平）。AI 不需要理解数字，只需要理解**语义位置**。

**② 档位文案是"叙事能力"而非"数值描述"**

```
根骨  5 档: "筋骨强健，精力充沛，寻常三五个壮汉也未必能轻易近身。"
悟性  8 档: "七窍玲珑，任何功法秘籍看上几遍便能领悟精髓，让人惊叹不已。"
心性 max : "道心稳固，万劫不磨，天崩地裂于前而色不变，已达圣人至境。"
声望  4 档: "名动一州，事迹在一州之内广为流传，是官府重点关注的江湖人物。"
```

**全部是可在小说里直接引用的意象**，不是"根骨 50/100"这种数字。这是这套写法最核心的价值：**它把数值翻译成了 AI 可以直接消费的叙事约束**。

**③ 档位之间有明确的"社会定位"锚点**

武学/学识/声望三组用了**外部社会坐标**而非主观感受：

```
武学 3 档: "……可入三流。"          武学 4 档: "……已是门派中的二流弟子"
武学 8 档: "一代宗师……足以担任名门大派的长老"   武学 max: "武林至尊"
学识 4 档: "……可中举人"            学识 8 档: "文坛泰斗……已是帝师级别的人物"
声望 3 档: "……官府和本地帮派都略有耳闻"  声望 6 档: "誉满天下，名声传遍大江南北"
```

这给 AI 提供了**可检验的行为边界**（"你现在这个水平，不该被人当宗师对待"）。

**④ EJS 承担"多分支个性化"**

L18–28 用 `userBackground` 的 A/B/C/D/E 五分支输出不同的"主角概述"，E 分支直接回填玩家自定义的 `userOriginDesc`。**世界书条目本身是动态的**，不是静态文档。

**⑤ 静默标签 `<%_ ... _%>`**

取值和 if/else 全部用**下划线静默标签**，渲染后不留空行，保证喂给 AI 的文本干净。这是 EJS 模板的规范用法。

### 7.4 这套写法的优缺点

**优点：**

1. **数值→叙事的一次性翻译，AI 零算术负担**。AI 永远看不到 `根骨=47`，只看"略有慧根…"。既防了 AI 算错，也防了 AI 在正文里写出数字。
2. **档位文案可复用为 UI 文案**。同一套文案在 tooltip 里给玩家看（`showAttrTooltip` L497–508 → `getAttributeTierText` L528–536），一份投入两处收益。
3. **边界清晰、不易幻觉**。"未曾习武…对江湖之事一无所知"比"武学 20"对 AI 的约束力强得多。
4. **省 token 且高信息密度**。每个属性只呈现**当前档**，不是 10 档全给。191 行覆盖 7 属性 + 5 出身分支。
5. **渐进升级有反馈**。跨档时文案突变（"资质平庸"→"中人之姿"），AI 能自然写出"今非昔比"的桥段。

**缺点：**

1. **双份维护、无同步机制**。EJS 版和 `attributeTierDescriptions`（`game-config.js` L84–169）靠注释约定一致，改一处漏一处就会 UI 与 AI 认知错位。
2. **档位边界是硬编码魔数**。`<11/<21/.../<91` 和 `<30/<60/.../<270` 散落在 EJS 与 JS 两处，改数值上限（`valueRanges`）不会带动分档。
3. **"当前水平"是单点信息，丢失趋势**。AI 知道你现在是"中人之姿"，不知道你上周是"资质平庸"，写不出成长弧光的细节。
4. **未体现装备加成**。`030` 里读的是 `gameData.playerTalents.根骨`（基础值），而玩家界面 tooltip 也刻意取基础值（`game-ui.js` L495–496 注释："取基础值（不含装备加成），与 LLM prompt 看到的数值一致"）。**这是一致性优先的取舍**——但意味着 AI 不知道你戴着 +根骨 3 的装备。
5. **依赖 EJS 插件**。纯 ST 环境若不装提示词模板/EJS 插件，`<%_ _%>` 会原样漏给 AI。
6. **属性名与代码耦合**。`gameData.playerTalents.根骨` 直接写在模板里，重命名属性会静默失效（EJS 抛错或被吞）。

## 8. 值得借鉴的 5 个点 / 应该避开的 3 个坑

> **筛选标准**：结合你的目标 ——「道具/技能/数值由代码控制，AI 只写剧情」。

### ✅ 值得借鉴的 5 个点

#### 1. 好感度"序数标签 → 代码映射整数"（`game-events.js` L441–467）

**做法**：AI 只能输出 5 个中文档位词（`大幅上升/上升/不变/下降/大幅下降`），代码用 `switch` 映射为 `+4/+2/0/-1/-2`，再叠加难度修正。

**为什么值得抄**：
- **AI 无法伪造数字**。这是"AI 只写剧情"最干净的一种落地：AI 描述"她对你笑了"，代码决定这值 +1 还是 +2。
- **难度调节是免费得到的**。同一句 AI 输出在 easy/hard 下自动不同，不需要改提示词。
- **和魅力属性天然联动**（`魅力/2` 概率加倍）。属性有了叙事之外的真实作用。
- **周上限机制**（`weekStartFavorability` 快照 + `5 + 魅力/20`）把"刷好感"变成受控资源。

**迁移建议**：任何"AI 决定倾向、代码决定幅度"的场景都适用——NPC 好感、门派声望、任务评价、恋爱进度。

#### 2. 发消息给 AI 前，主动剥离代码演算细节（`game-helpers.js` L56–71）

**做法**：`handleMessageOutput()` 在 `/inject` 之前，把消息里 `属性变化` 和 `计算过程` 之后的全部内容**截掉**。

```js
const attrChangeIndex = message.indexOf('属性变化');
if (attrChangeIndex !== -1) message = message.substring(0, attrChangeIndex).trim();
const calcProcessIndex = message.indexOf('计算过程');
if (calcProcessIndex !== -1) message = message.substring(0, calcProcessIndex).trim();
```

**为什么值得抄**：
- 玩家能看到"武学 +3（心性判定成功，行动点 -0）"，但 **AI 看不到**。AI 只知道"你练武成功了"。
- 这从根上杜绝了 AI 复读数值、AI 自行推算数值、AI 抱怨数值不合理。
- 实现成本极低（两个 `indexOf` + `substring`），收益极大。**这是全项目性价比最高的一段代码。**

#### 3. 特殊事件：预写剧本 + `/sendas` 注入（`special-event.js` L4607–4712）

**做法**：57 个事件，每个带 `conditions`（嵌套路径 + min/max/equals/in）、`effects`（set/add/multiply/push/remove/concat）、`text`（完整 SLG_MODE 文本）。条件命中就 `applyEventEffects()` 改数值，然后 `/sendas` 把预写文本当成 AI 回复发出去。

**为什么值得抄**：
- **关键剧情节点的质量下限有保证**。日常交给 AI 自由发挥，主线节点走手写剧本——这是商业游戏的做法。
- **`conditions` 是声明式的**，支持 `npcFavorability.C: {min: 60}` 这种嵌套路径，写起来接近配置。
- **`effects` 是通用的变量操作语言**（6 种操作），不限于数值，`companionNPC: {push:'苓雪妃'}` 直接改数组。
- **事件链机制**（`currentSpecialEvent` + L4576–4586 的"续接优先"扫描）解决了"高优先级新链抢占导致断链"这个真实 bug，注释写明了原因。

**迁移建议**：把"必须发生对的"剧情（拜师、结盟、背叛、结局分支）预写成事件，其余交给 AI。

#### 4. 数值范围集中声明 + 统一夹紧入口（`game-config.js` L51–79 + `game-utils.js` L64–106）

**做法**：所有数值范围在一个 `valueRanges` 对象里声明；`checkAllValueRanges()` 是**唯一**的夹紧入口，在每个改动数值的地方末尾调用（`performAction` L2410、`applyEventReward` L156/L165、`parseLLMResponse` L461/L557/L717、`useItem` L1302、`equipItem` L1370、`applyEventEffects` L4543…）。

**为什么值得抄**：
- **AI 给什么离谱数字都能兜住**。`applyEventReward` 直接正则抠 AI 字符串里的数字（`悟性+3`），但立刻 `checkAllValueRanges()`，最坏情况也只是撞到上限 100。
- **范围声明同时是 UI 的分母**。`updateStatsDisplay()` L249 用 `Math.min(100, totalTalents.根骨)+'%'` 画进度条，范围直接复用。
- **一处改，处处生效**。

**注意它的取舍**（**【读到】** L72、L88–96 的注释）：天赋和战斗基础值**只保证是数字、不做范围夹紧**，只有 `playerStats` / `playerMood` / `npcFavorability` / `actionPoints` / `currentWeek` 真正夹紧。这是有意为之（战斗中允许临时超限），但**也意味着 `combatStats` 可以被道具/事件顶穿上限**——`getTotalCombatStats()` L153 在读取时才夹紧。抄的时候要明确选哪种策略。

#### 5. LLM 输出的"五级瀑布匹配 + 语义兜底"（`game-utils.js` L451–520 + 两套关键词表）

**做法**：
```
精确匹配 → 同义词精确 → 双向包含 → 同义词包含 → Levenshtein 相似度(阈值)
   ↓ 全失败
sceneSemanticKeywords / emotionSemanticKeywords 逐关键词 includes
   ↓ 再失败
返回 'none'
```

**为什么值得抄**：
- **LLM 输出枚举值时几乎必然会漂移**。它会写"戈壁"而不是"沙漠"，写"红透了脸"而不是"害羞"。硬编码精确匹配 = 天天出 bug。
- **同义词表覆盖"常见近义"**（`slgSceneSynonyms` L619–666 有 20+ 组），**关键词表覆盖"幻觉长尾"**（`sceneSemanticKeywords` L800–888 连单字"山/水/洞/派/店/城/村"都兜）。
- **`legacySceneOptions` 处理"版本迁移期 AI 还会吐旧值"**（L670–679 + L547–549 精确匹配旁路）—— 这是很成熟的兼容思路：**旧值走旧规则，新值走新规则，不要混用模糊匹配**。
- **阈值按字段调**（场景 0.4 宽容 / 表情 0.5 / NPC 0.6 严格），注释解释了为什么场景要更宽容。

**迁移建议**：任何"AI 输出必须落到有限枚举"的地方（场景、表情、立绘、CG、BGM 基调、NPC 名）都该有这套。

### ⚠️ 应该避开的 3 个坑

#### 坑 1：用"启发式字符串切片"解析 AI 的结构化输出（`index.html` L1841–2009）

**问题代码**：

```js
// 抓正文：从第一个汉字/#/* 到第一个 <
const mainTextMatch = slgModeContent.match(/[#*\u4e00-\u9fff\u3400-\u4dbf...][^<]*/);
const startIndex = slgModeContent.indexOf(mainTextMatch[0]);
const endIndex = slgModeContent.indexOf('<', startIndex);

// 抓 JSON：从第一个 { 到下一个 <
const jsonStartIndex = slgModeContent.indexOf('{');
const jsonEndIndex = slgModeContent.indexOf('<', jsonStartIndex);
const jsonText = slgModeContent.slice(jsonStartIndex, jsonEndIndex);
JSON.parse(jsonText);   // ← 裸 parse，无 try 之外的保护
```

**为什么是坑**：
- **正文里只要出现一个 `<` 就截断**（剧本里 `她的声音<颤抖>` 之类直接毁掉）。
- **JSON 里只要出现 `<` 就截断**，且**取的是全文第一个 `{`** —— `<ANAL>` 是 YAML 不是 JSON，但 `MAIN_TEXT` 正文里写一个 `{`（比如"你心想{这下完了}"）就会让 JSON 从错误位置开始。
- `JSON.parse` 后面虽然是 `try/catch`（L1995–2006），但**失败就是静默放弃整轮数值结算**（只 `console.error('解析SIDE_NOTE失败:', error)`），玩家看不到任何提示，游戏状态悄悄少更新一次。
- 摘要抓取还有一段更离谱的"鲁棒方法"（L1913–1984）：从第一个 `{` **往前**找汉字，再**继续往前**找 `>`，然后把中间那段当摘要。这段代码几乎必然在正常情况下也抓到奇怪内容，注释坦白叫"可能的 SUMMARY 内容"。

**正确做法**（项目自己后来也做了）：**上 `jsonrepair` 之类的容错解析库**。`index.html` L1311 已经引了 `module/vendor/jsonrepair.min.js` + L1312 `json-repair-helper.js`，但 L5576–5578 显示 **ST 链路仍然走老 `parseOutput()`**。**你新写的时候直接上 JSON 修复 + 显式 XML 标签提取，别复刻这套。**

#### 坑 2：`gameData` 是超大扁平对象，且"全局变量镜像"靠手工同步（`game-state.js` L62–310）

**问题**：
- `gameData` 一个对象塞了 **60+ 个字段**，含 15×5 个 NPC 相关的平行字典（`npcFavorability`/`weekStartFavorability`/`npcLocations`/`npcVisibility`/`npcGiftGiven`/`npcSparred`），**每次存档要全量 `JSON.stringify` 写进一个 ST 变量**。
- `syncVariablesFromGameData()` L180–255 是**一坨 76 行的解构赋值**，`syncGameDataFromVariables()` L258–310 是**一坨 53 行的手工逐字段写回**。**加一个字段要改两个地方，漏一处就静默不同步。**
- 更糟的是还有第三份：`index.html` L5540 的 `gameData._activeEvent` 这种"临时塞进存档字段"，用完 `delete`。
- NPC 位置有**两套表示**：`currentNpcLocations`（对象）+ `npcLocationA`…`npcLocationO`（15 个独立全局变量），`game-events.js` L582–599 还得写一个 15 分支的 `switch` 来同步。加角色要改 6 个字典 × 2 个同步函数 + 1 个 switch。

**代价（**【读到】** 已经有真实的坑）**：
- `game-state.js` L508–515 `saveGameData()` 里有 **`if (!renderFunc) return;` 紧跟 `if (!renderFunc) {` 的重复判断**，导致**第一个 `return` 直接把 standalone 分支变成了死代码**：
  ```js
  async function saveGameData() {
      const renderFunc = getRenderFunction();
      if (!renderFunc) return;              // ← L509 已经返回了
      if (!renderFunc) {                    // ← L510 死代码，永远不执行
          syncGameDataFromVariableSystem();
          storageService.saveAppState({ gameData: gameData });
          return;
      }
      ...
  }
  ```
  这正是"重复样板代码太多导致 review 失效"的典型症状。
- `game-config.js` L349–366 `npcSparRewards` 的注释与实际值**大面积不符**（`A: {type:'武学', value:5}` 注释写"破阵子 - 武学+3"；`C: value:500` 注释写"金钱+300"）。L935–941 `dangerEventChance` 同样（`'低': {battle:0}` 注释写"战斗5%"）。
- `index.html` L2497 `npcsToShuffle` 里**仍然带着已废弃的 `'Z'`**（`npcVisibility['Z']` 是 `undefined`，`!undefined === true`，于是 `currentNpcLocations['Z'] = 'none'` 被创建 —— 一个幽灵字段）。

**正确做法**：字段分组（`time`/`player`/`npcs`/`world`）、NPC 数据用**数组 of 对象**或按 id 索引的单表、同步用 `Object.assign` + schema 驱动，别手写两遍。**（本项目缺失的 `module/variable-system.js` 里的 `hydrateVariableSystemFromGameData()` 看名字就是在做这件事——但文件不在，无法确认。）**

#### 坑 3：`special-event.js` 把 382 KB 中文小说塞进 JS 源码

**问题（**【读到】**）**：
- 4740 行文件里，**绝大部分是 57 个事件的手写剧情文本**（`text: \`<SLG_MODE>...\``，单个事件 50–100 行）。
- 这些文本和代码**在同一个文件、同一层作用域**，语法高亮、搜索、diff 全部失效。
- 文本里含 `|`（五段式分隔符）和反引号的风险 —— 所以 L4691–4693 才必须做转义：
  ```js
  const safeText = event.text.replace(/\|/g,'\\|').replace(/`/g,'\\`');
  ```
  **这本身就是"数据放在代码里"的代价**。
- **无法做本地化/多语言**，无法让策划改文案而不碰代码，无法按需加载（整个 382 KB 在页面初始化时就要解析）。
- 剧情文本里如果出现 `${...}` 还会被模板字符串插值 —— 这是**潜伏的运行时炸弹**。

**正确做法**：剧情文本外置为 JSON / Markdown / 独立 `events/*.txt`，运行时按需 `fetch`（ST 卡场景下用 `_assetUrl()` 从 CDN 拉）。事件表只留 `id/priority/conditions/effects/textRef`。这样：
- 源码回到几百行
- 文案可单独维护、可 diff
- 大文本可懒加载（57 个事件大部分一局游戏都不会触发）
- `|`/反引号/`${}` 的转义问题彻底消失

## 9. 一页速查

| 维度 | 结论 |
|---|---|
| **架构本质** | "AI 写剧本、代码当裁判"的**混合叙事引擎**。ST 只是个跑 iframe 的宿主 + 变量仓库，游戏逻辑 100% 在 JS 里。 |
| **持久化** | 单个 ST 变量 `gameData`（`/setvar`/`/getvar` 全量 JSON），standalone 模式用 IndexedDB。 |
| **AI 调用方式** | `/inject role=user` + `/trigger`（日常）；`/sendas`（预写剧本）。**没用 `generate()`**。 |
| **AI 输出协议** | `<ANAL>`(YAML 思维链) + `<SLG_MODE>{<MAIN_TEXT>`五段式`<SUMMARY><SIDE_NOTE>`JSON`}`。 |
| **数值主权** | 主线数值（属性/战斗/资源/物品）**完全归代码**；支线（事件奖励/成功率/战斗报酬/掉落档位）**AI 提名、代码盖章**。 |
| **发 AI 前会剥离什么** | `属性变化` 和 `计算过程` 两段（`handleMessageOutput` L56–71）。**AI 永远看不到数值增量。** |
| **战斗** | 纯代码回合制，跑在 `turn-based-battle-new.html` iframe 里，URL 传参进、`postMessage` 出。**AI 只在战前定敌方档位、战后写剧情。** |
| **AI 输出的容错** | 五级模糊匹配（精确→同义词→包含→同义词包含→编辑距离）+ 两套语义关键词兜底 + `legacySceneOptions` 版本兼容。 |
| **最大的性能/维护债** | ①`parseOutput` 启发式字符串切片 ②`gameData` 60+ 字段手工双向同步 ③382 KB 剧情硬编码进 JS |
| **最值得抄的一句** | `handleMessageOutput()` 里那两行 `indexOf` + `substring` —— 用两行代码把数值彻底挡在 AI 上下文之外。 |
| **最该先做的改造** | 把 `special-event.js` 的 `text` 外置成数据文件；把 `gameData` 拆成分组 schema。 |
