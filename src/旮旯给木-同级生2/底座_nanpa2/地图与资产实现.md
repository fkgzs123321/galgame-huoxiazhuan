> 回答三个问题：**地图能干什么** / **地图、人物画像、场景按 skills 怎么实现**。

## 一、地图能干什么（三个功能，互相咬合）

你提的三个方向都成立，而且**它们不是三件事，是一个闭环**。

### F1 · 时间消耗的判定 ——「去一趟要花多少」

原作明写「游戏内有钟，去一个地方或见一个人都消耗三周时间的一小部分」。

**机制化**：每个地点有一个**距离成本**，移动就扣时间。

```yaml
地点距离:
  自宅周边:   0     # 基准
  八十八学园: 1
  商业区:     1
  88车站:     2
  温泉乡:     3     # 远
  ...
时间成本 = 目标地点.距离
扣减对象 = 时间.时段进度（不是直接跳一个时段）
```

### F2 · 位置关系的描述 ——「能不能顺路」

- **相邻性**：从 A 到 B 要不要经过 C
- **归属**：哪些地点在同一个建筑内（学园的 6 个子地点就是「进一次学园内的不同房间」）
- **可达性**：某些地点在特定时段才开（学校放学后、店铺打烊）

**用途**：决定「一次出行能覆盖几个地点」。这是**她排时段的实际约束**——
不是「一天只能去一个地方」，而是「一天的时间只够覆盖这么多距离」。

```
学园内移动      成本 0（同一次出行内）
同区域移动      成本 1
跨区域移动      成本 2~3
不可达          该时段关门（学校夜间 / 店铺打烊）
```

### F3 · 遇到人物的情况 ——「到了那儿有谁」

这是**原作的驱动方式**：

```
(日期, 时段, 地点)  →  在场名单  →  可发生的互动
```

原卡已有 `人物出现总表`（`getAvailableHeroines(day, timeSlot, region)`），
**但它的 region 只有 7 个**，而原作约 30 个地点 → **要扩**。

### ⭐ 三个功能咬合成什么

```
地点  →  决定遇到谁（F3）
地点  →  决定花多少时间（F1）
距离  →  决定一次出行能覆盖几个地点（F2）
        ↓
   她一天只有 5 个时段
        ↓
   【地图 = 她的资源分配问题的场地】
```

**这才是地图真正的功能**：它不是背景板，它是**她必须做取舍的地方**。

> 地点越多，取舍越难；取舍越难，她的每一次选择越有分量。
> **这就是为什么原卡 7 个区域不够** —— 选择太少，她随便点点就覆盖完了。

## 二、地图按 skills 怎么实现（两层）

### 层 1 · 地理条目（世界书）

按 `geography.md` 的规范：

| part | 内容 | 同级生2 的对应 |
|---|---|---|
| **region** | 区域概览（地理特征、主要地点、势力分布） | 「八十八町」「如月町」「温泉乡」等**区域级**条目 |
| **scene** | 单个场景的具体描写 | 「保育园」「咖啡厅《憩》」「88 公园」等**地点级**条目 |
| **faction** | 势力详情 | 同级生2 没有势力对抗 → **不用这个 part** |

**拆分时机**（规范原文）：「信息量足够时才拆——判断标准：场景或势力的内容独立成段后，
是否比留在区域条目里更清晰？**是否需要通过条目显隐控制 token**？」

→ 同级生2 约 30 个地点，**必须拆**（否则区域条目会变成一坨，且无法按需加载）。

**地理速览**（规范原文）：「当区域数量超过 5 个且有大量单独的场景条目，可以考虑编写地理速览，
列出区域名称、地点/场景的名称。」

→ 同级生2 有 7 个区域 / 约 30 个地点 → **必须写地理速览**。
它同时充当**在场名单查询的索引**（见 F3）。

### 层 2 · 地图数据（契约表）

`geography.md` **只规定了文字条目的写法，没规定「地图作为机制数据」怎么写**。
所以这一层由我们的 T1 契约承担：

```yaml
# 追加到 状态表.yaml 的 T1 时间表
地点:
  <地点名>:
    区域: <区域名>
    距离: <0~3>              # 从自宅出发的成本
    开放时段: [早, 上午, 下午, 晚]   # 学园夜间不可达
    在场名单: (日期, 时段) → 女角列表   # 见 F3
```

**这一层是孪生2 的「地图机制」，不是 skills 的规范内容** —— skills 管文字条目怎么写，
我们管机制怎么跑。

### 层 3 · 地图界面（可选，用 embedded-ui）

如果要画一张**可点的地图**，那是 `sillytavern-embedded-ui` 的活。
**但我不建议现在做**：

- 她有 5 个时段要排，那是**她要做的决策**，不该由玩家界面替她做
- 玩家看到地图只会变成「我也想去那儿」——而**玩家本来就不能决定去哪**
- 地图作为**数据**已经足够支撑机制

> 结论：**地图先做数据和文字条目，不做界面。** 界面留到「状态栏需要展示
> 『她今天去了哪』」的时候再做。

## 三、人物画像与场景资产（按 media skill）

### 先说一个硬约束（必须先知道）

`tavern-cards` 规范里关于图片，**只有一处**：

```
type/state.ts:  avatar: z.string().optional().describe('头像 PNG 路径, 相对于项目根目录')
conventions.md: 项目根目录：avatar.png（仅角色卡有头像时）
                .png = 嵌入 JSON 的 PNG 图片（有头像时） / .json = 无头像时
```

**SillyTavern 角色卡只有一张头像（`avatar.png`），卡内没有「立绘」「场景图」的容器。**

所以 15 位女角的立绘、30 个场景的背景图**不能靠卡本身携带**。它们只能：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 外链** | 图片托管在 HTTPS 地址，界面里 `<img src="...">` | 需要图床；**外链会失效** |
| **B 只用一张** | 15 位女角共用一张卡面 —— 等于没有立绘 | 没有差异化 |
| **C 不引入图片** | 人物画像和场景**全部用文字**（skills 的 `basic-info.md` 就是这套） | 没有视觉 |

**我的建议：C 为主，A 作为可选增强。**

理由：`basic-info.md` 的规范就是「**写外貌不是写美，是写特征**」——
它预设的载体是**文字**，而且明确禁止「过度细节（每个五官都写一遍）」。

> 画像的真正载体是**文字**。图片是锦上添花，而且会带来外链失效、图床迁移、
> 加载失败等一堆运行时问题 —— 那与「卡要稳定」相冲突。

### 如果确实要做媒体资产 —— 按 media manifest contract

```json
{
  "schemaVersion": 1,
  "cardId": "galgame-nanpa2",
  "assets": [
    {
      "id": "heroine-narusawa-yui",
      "kind": "image",
      "source": { "type": "local", "path": "媒体/人物画像/鸣泽唯.png" },
      "bytes": 0,
      "sha256": "",
      "preload": "on-demand",
      "lifetime": "message",
      "fallbackAssetId": null
    }
  ]
}
```

**契约的硬约束**（原文档规定）：
- `kind` 只能是 `audio` / `image` / `video` / `multimodal` / `live2d-model` / `live2d-motion` / `live2d-expression`
- `preload` = `eager` / `lazy` / `on-demand`；`lifetime` = `card` / `chat` / `message`
- 本地源用安全相对路径；**远程源必须 HTTPS 且可声明 SHA-256 与字节数**
- **静态校验绝不下载**（「Do not contact remote URLs during the static audit」）
- `fallback` 必须指向另一个已声明的资产，不能指向自己

**同级生2 的合理取值**：
```
人物画像：kind=image, preload=on-demand, lifetime=message
          （只在某位女角出场时才需要，不该预载）
场景图  ：kind=image, preload=on-demand, lifetime=message
BGM     ：kind=audio, preload=lazy,    lifetime=chat
```

> ⚠️ **preload 预算**：media skill 明确要求「deterministic preload budgets」。
> 15 立绘 + 30 场景图如果 eager 预载 = 灾难。**全部 on-demand**。

### 场景资产分两层（别混）

| 层 | 是什么 | 放哪 |
|---|---|---|
| **场景文字** | 这个地点长什么样、有什么声音和气味 | 世界书 `地理` 条目的 `scene` part |
| **场景图** | 这个地点的画面 | 媒体资产（`kind: image`，可选） |

**文字是主，图是辅。** 而且 `geography.md` 已经规定了文字该怎么写。

## 四、结论与建议

| 资产 | 载体 | 优先级 |
|---|---|---|
| **地图** | 世界书 `地理`（region + scene part）+ **地理速览** | **必做** |
| **地图机制数据** | T1 契约的扩展段（地点 / 距离 / 开放时段 / 在场名单） | **必做** |
| **人物画像** | **文字**（`basic-info.md` 的外貌特征） | **必做** |
| **场景** | **文字**（`geography.md` 的 scene part） | **必做** |
| 人物立绘（图） | 媒体清单（`kind: image`, `preload: on-demand`） | 可选 |
| 场景图 | 同上 | 可选 |
| 可点地图界面 | `sillytavern-embedded-ui` | **暂不做**（见 §二 层 3） |

## 五、待你定

1. **人物画像 / 场景图要不要做？**
   - 不做（纯文字）：零运行时风险，符合 skills 的写法规范
   - 做（外链图床）：有视觉，但要承担外链失效、图床迁移、加载失败
   - **我建议先做纯文字，把图留到最后**——因为重点是机制和内容，图可以随时补
2. **地图界面做不做？** 我建议不做（理由见 §二）
3. **地点数**：7 个区域扩到约 30 个地点，`人物出现总表` 要按新地点重做 —— 确认开工？
4. **「八十八海岸」**：原作找不到，删掉还是留着当自创地点？
