# 同级生2 · 模块化设计

> **主责文档。** 把 `src/同级生2/`（一张已完成但结构混乱的大卡）解剖成「机制层 / 内容模块 / 项目框架」三部分，
> 使其：① 自身符合 tavern-cards 规范；② 通用机制可被 `旮旯给木` 引擎层吸收。
>
> 主干：**tavern-cards（B）**。配套：`旮旯给木-同级生2/design-spec.md`（引擎+底座设计）、
> `scripts/verify-prompt-budget.mjs`（预算校验器）。

## 一、诊断：原卡走错了工具链（实测数据）

### 1.1 根本病因

| 事实 | 证据 |
|---|---|
| 原卡用的是 **tavern_sync** 格式，不是 tavern-cards | `index.yaml:1` 的 schema 指向 `tavern_sync/dist/schema/character.zh.json`；字段是中文键名（`条目`/`插入位置`/`激活策略`/`蓝灯`/`绿灯`/`启用`） |
| **`tavern-cards-state.json` 是空壳** | `entryManifest` 全空、`typeLists` 全空、`strategyThresholds` 全空、`first_messages` 只有一条 |
| → 结论 | **这张卡从来没有跑过 `configure`**。所有投放配置是手工填在 `index.yaml` 里的 |

后果：没有自动推导、没有校验、规则靠手填——所以下面这些问题全部存在。

### 1.2 实测问题清单（203 个条目）

| # | 问题 | 实测 | 严重度 |
|---|---|---|---|
| 1 | **违反 skills 铁律：用了 depth 1-4** | **16 条**（depth1×3 / depth2×4 / depth3×6 / depth4×3） | **P0** |
| 2 | **四成条目是关着的** | `启用: false` **85 条 / 203 = 42%** | **P0** |
| 3 | 位置分布严重失衡 | 角色定义之前 65 / **角色定义之后仅 3** / 指定深度 16 | **P0** |

### 1.3 最讽刺的一处

**原卡把最重要的护栏规则放进了 depth 1-4**，而这正是 skills 明令禁止的：

```
防口胡 (depth 2)      防神化 (depth 3)      防绝望 (depth 3)
防全知 (depth 3)      防崩溃 (depth 2)      防超自然 (depth 2)
道德伦理 (depth 2)    法律意识 (depth 3)    经济护栏 (depth 3)
```

按 skills 规范：`扮演准则` 类应放 `before_char` 且 `strategyThresholds: Infinity`（强制常驻）。
**原卡不仅位置错，还把 16 条规则塞进了深度注入——越贴近对话历史的位置越容易被后文覆盖。**

> `configuration.md:23`：**D1+ 深度绝对禁止使用**

## 二、技术手段矩阵（"怎么保证机制层不被覆盖"）

用户问：世界书深度、顺序、思维链、正则、脚本能做好吗？
**能，但这 14 个手段必须分工，不能混用。** 以下全部来自 skills 规范原文核实。

| # | 维度 | 手段 | 语义 | 用途 |
|---|---|---|---|---|
| 1 | **类型** | `typeLists` 的三个列表 | `before_char` → `before_character_definition`；`after_char` → `after_character_definition`；`depth` → `at_depth` | **决定 position + collection order**（引擎类型排前，底座类型排后） |
| 2 | **scope** | `catalog` | 始终 constant，不参与同 part 计数 | 引擎条目强制常驻 |
| 3 | **策略阈值** | `strategyThresholds = Infinity` | 始终 constant | 引擎/护栏强制常驻 |
| 4 | 同上 | `strategyThresholds = 0` | 始终 selective | 底座按需层强制关键词 |
| 5 | 同上 | `strategyThresholds = null` | 禁用 | 临时停用不删文件 |
| 6 | **位置** | `before_character_definition` | 角色核心描述**之前** | 引擎规则（最前） |
| 7 | 同上 | `after_character_definition` | 角色描述之后 | 角色人设类 |
| 8 | 同上 | `at_depth` | 需配合 depth | **⚠️ 铁律：只能 depth 0** |
| 9 | **顺序** | `order`（tens-group：起始10，逐条+1，跨类型跳整十） | 数字**越小越先注入** | 同位置内排序。**手工填的值不会被 configure 覆盖**，但新加条目会自动分配→需重新校正 |
| 10 | **思维链** | `injectPrompt("CoT", ...)` + 预设里 `<%- getPromptsInjected("CoT") %>` | 世界书定义 CoT，**投放到预设的思维链位置** | ⭐ **AI 注意力最高区**。把「推演链 + 加载纪律」放这里，比放世界书有效得多 |
| 11 | **正则** | `regex_scripts` | 消息文本匹配/替换/隐藏 | **只做显示层**（隐藏变量块、上色）。规范明言："前端界面的正则只负责定位、不解析数据" |
| 12 | **脚本** | `脚本/`（TavernHelper） | 后台逻辑、事件监听 | **只做确定性计算**（LCG 骰子、判定）。不承载叙事规则 |
| 13 | **互斥组** | `group: { labels, use_priority: true, weight }` | 同组只激活权重最高的条目 | ⭐ **20 女角条目同组 → 只注入当前在场的那一个**（比 keywords 更可靠） |
| 14 | **时间行为** | `effect: { sticky, cooldown, delay }` | 激活后持续 n 条 / 停用后 n 条不能再激活 / 至少 n 条后才能激活 | 按楼层控制条目生命周期 |
| 15 | **EJS** | `@@if` 前缀条件 | 变量条件直接控制渲染；**同 part 中最多计为 1** | ⭐ 最精确的按需加载（按天/按关/按人） |
| 16 | **强常驻** | `@@activate` 装饰器 | 忽略关键词，当作常驻 | 核心规则的兜底保险 |

### 决策优先级（判据）

```
能用 EJS 变量条件解决的   → 不要退回正则
能在显示层用正则解决的     → 不要写进世界书正文
需要确定性计算的           → 交给脚本，不要写进叙事条目
最重要的规则               → injectPrompt("CoT")，放预设思维链位置
需要互斥的同类内容         → group.use_priority，不要靠 AI 自觉
```

**当前 euphoria 只用了 #1/#2/#3/#6/#7/#9/#15 —— 思维链（#10）、互斥组（#13）、时间行为（#14）三个维度完全没用。**

## 四、迁移方案（tavern_sync → tavern-cards）

### 步骤

```
1. 写转换脚本 scripts/migrate-index-to-plan.mjs
   读 index.yaml（tavern_sync）→ 产出 创作规划.yaml 的 entries 段 + state 的 typeLists

2. 中文键名 → tavern-cards 字段
   插入位置.类型       → position.type
     角色定义之前       → before_character_definition
     角色定义之后       → after_character_definition
     指定深度           → ⚠️ 全部改为 before_character_definition（消掉 16 条违规）
     脚本               → 移出世界书，进 脚本/ 目录
   插入位置.顺序       → position.order
   激活策略.类型       → strategy.type
     蓝灯               → constant
     绿灯               → selective
   启用                → enabled

3. 重建 typeLists（关键！顺序决定一切）
   before_char: [引擎机制, 扮演准则, 世界观, 时间线, 地理]
   after_char:  [角色, NPC, 底座内容]
   depth:       [事件, MVU]

4. 重建 strategyThresholds
   引擎机制/扮演准则/世界观/阶段指导 → Infinity（强制常驻）
   角色/NPC                          → 0（强制关键词触发）
   事件/MVU                          → Infinity

5. 跑 configure → 自动推导全字段
6. 跑 verify-prompt-budget.mjs → 对比基线
7. 逐条处理 85 条 启用:false
```

### 注意

- **不要手改 order 后直接跑 `configure --force`** —— 会覆盖手工值。正确做法是先建好 `typeLists`，让 tens-group 自动算对。
- **`指定深度` 的 16 条不能简单改成 before_char** —— 它们是「护栏规则」，改完要确认不与已有条目重复（如 `核心铁律` 与 `防口胡` 可能重叠）。
- **转换 ≠ 重构**。转换只解决格式；三层解剖（拆 D0 / 角色性格控制器 / 全局规则总表）是独立的一步。

## 八、清理清单（审计器实测 · 2026-09-15）

工具：`scripts/audit-nanpa2.mjs`（`--entries` / `--vars` / `--all`）
判据：用户定 —— **有调用者就留、无调用者就删；数值必须有落脚点、有计算、有意义，否则删**

### 8.1 变量：129 个 → 目标约 70 个

| 分类 | 数量 | 处置 |
|---|---|---|
| 孤儿（全卡零接触） | 17 | **全删** |
| 无落脚点（有写无读） | 35 | 逐个判：删 / 接线 |
| 无计算（有读无写） | 17 | **补写点或删**（见 C） |
| 疑似重复（同名末段） | 17 组 | 合并 |
| OK（读写俱全） | 60 | 保留 |

#### A. 直接删除：`当前女角` 的属性与技能副本（18 个）

```
当前女角.魅力 学业 体力 社交 敏感 声誉              ← 与 主角.* 重复
当前女角.力量 敏捷 智力 潜行 口才 医学 烹饪 艺术 驾驶 格斗 观察 意志技能 恋爱技能  ← 与 技能.* 重复
```

> **但 `当前女角` 不能整个删。** 实测它的另一部分是活的：
> `当前女角.H经验次数`（**20 次公式参与**，全卡第一）、`当前女角.关系阶段`（18 次）、
> 好感度 / 心动值 / 嫉妒值 / 信任度 / 湿润度 / 兴奋度 都在被读。
> **结论：`当前女角` 收窄到「关系值 + 即时 NSFW 状态」，删掉属性与技能副本。**
> 理由：`calcPlayerPower()` 读的是 `主角.*` 和 `技能.*`，女角身上那份从来没人读。

#### B. 经济双轨合并（9 个 → 4 个）

现状**两套并存，且两套都没人读**：

```
主角.储蓄 / 储蓄目标 / 今日餐费 / 今日礼费 / 今日交通费 / 今日总消费
经济.当日收入 / 当日支出 / 累计储蓄
```

处置：保留 `主角.现金`（活的）+ `经济.当日收入 / 当日支出 / 累计储蓄`，删掉 `主角.储蓄` 系列。

> ⚠️ **合并后必须接线**：`累计储蓄` 是 True End 的硬条件（储蓄 ≥ 50000）。
> 现在没有任何地方读它 —— 也就是说**原卡的 True End 判定读的是一个没人更新的值**。

#### C. 补写点：6 属性 + 12 技能（18 个）—— ★ 最大的机制漏洞

```
主角.魅力 学业 体力 社交 敏感 声誉
技能.力量 敏捷 智力 潜行 口才 医学 烹饪 艺术 驾驶 格斗 观察 意志 恋爱
```

实测：**有读点（`calcPlayerPower()` / `LCG骰子引擎` / `角色性格控制器` 都在读），但没有任何写点。**

查证 `变量更新规则.yaml`：只有两条提到属性，且**全是约束不是触发**：

```
- 魅力 / 学业 / 体力 / 社交 / 敏感 / 声誉：单轮参考上限 ≤ 5 点     ← 变化幅度约束
- 跨时段累积变化无上限（如多日累积可让 魅力 从 50 涨到 80）        ← 累积说明
```

**没有一条说「做了什么会涨」。** 且该文件里**完全没有 `stat_data` 路径**，全是自然语言。

**后果**：属性永远停在初始值 → `calcPlayerPower()` 的输出恒定 → **整套骰子判定形同虚设**。
玩家看到的「判定成功/失败」其实是 AI 即兴编的，不是算出来的。

这同时印证了 `design-spec.md §7.1`：**「她的后果必须来自确定性计算，不能 AI 即兴」是引擎唯一的漏洞，原卡这里是同一个洞。**

**处置**：在变量更新规则里补齐**明确的触发条件**（什么行为涨哪个属性、涨多少、上限多少）。
